# 识别速度实测（0.3.1）

> 测法：`tests/perf/latency.js` 直接驱动**打包版 sidecar**（真实 JSON 协议），
> 每档先预热一次，再取 2–3 次的中位数；「首次出字」= 收到第一条 `result` 的时间，
> 「最终结果」= 收到 `refined`（无两段式的版本两者相同）。
> 对照版本：0.2.4 侧车（`python/ocr_pkg_prev_024_old/`，与 0.3.1 同机同图背靠背测）。
> **本机有后台负载（视频/IDE），绝对值会漂；看倍数不看绝对值。**

## 1. 2K 整屏（2560×1600，17 行）

| 档位 | 版本 | 首次出字 | 最终结果 |
|---|---|---:|---:|
| fast | 0.2.4 | 320ms | 320ms |
| fast | 0.3.1 | 331ms | 331ms |
| balanced | 0.2.4 | 866ms | 866ms |
| balanced | 0.3.1 | 795ms | 795ms |
| **accurate** | 0.2.4 | **9139ms** | 9139ms |
| **accurate** | 0.3.1 | **787ms（11.6×）** | 9960ms（+9%） |

| 档位 | 版本 | 首次出字 | 最终结果 |
|---|---|---:|---:|
| fast | 0.2.4 | 297ms | 297ms |

## 4. 结论

1. **高精度档感知提速 3.5–11.6×**：选区越大、行数越多，收益越明显（原来要等整段 medium 跑完）。
2. **终态会略慢 6–33%**：两段式等于「small 先跑一遍 + medium 再跑一遍」，
   多出来的正是那次 small（约 0.5–0.8s）。行数少的选区占比更高，所以 4 行场景 +33% 最明显。
3. **均衡 / 快速档几乎不变**（±10%，属机器负载波动）：两段式只对高精度档生效。
4. **用户实际感受**：加上截图（约 0.9s）与窗口渲染，高精度档「按下快捷键 → 看到文字」
   从约 10–11s 降到约 1.7–1.9s；完整结果仍在后台 9–12s 内补齐，不挡人。

## 5. 复现

```bash
node tests/perf/latency.js --image shot-2560 --runs 2                       # 当前版本
node tests/perf/latency.js --image shot-2560 --runs 2 \
  --exe python/ocr_pkg_prev_024_old/ocr_server.exe                          # 对照旧版
node tests/perf/latency.js --profile accurate --runs 3 --image lines-4      # 单档位
```

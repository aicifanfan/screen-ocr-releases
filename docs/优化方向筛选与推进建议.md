# 性能优化：本地可行性与方向筛选

> 目标：从《OCR识别加速方案》的 16 项里，挑出**在当前机器、当前工程条件下真正能落地**的那几条，
> 并给出推进顺序、验收门禁与回滚方式。
> 结论先行：**推荐 A1 + B1 + C1 打包成 0.2.4**；E1（两段式）单独排 0.3.0；F1/F2/G1 本轮不做。

---

## 1. 本地环境盘点（实测）

| 项 | 现状 | 对选型的影响 |
|---|---|---|
| CPU | **32 逻辑核**（`os.cpus()` = 32） | 线程上限放开的收益上限高；但要让出 2 核给 UI/系统 |
| 内存 | 15.7 GB | 够跑两个 sidecar 做 A/B；不适合常驻双模型 |
| 磁盘 | C: 66 GB 可用 | 够装 venv（~500 MB）+ 量化中间产物 |
| PyPI | `pypi.org/simple/rapidocr` **200 / 0.42s** | 可以现场建 Python 环境 |
| 模型源 | ModelScope 直链 **200** | 重打包后即便缺模型也能自动补下载 |
| Python | 系统 python **无** rapidocr；uv 自带 **3.12.14** | 需要一次性建 venv（可创建，非阻塞） |
| 现役运行时版本 | `rapidocr 3.10.0` / `onnxruntime 1.20.1` / `numpy 2.5.4`（从包内 `*.dist-info` 读出） | 重打包必须**钉死这三个版本**，否则行为漂移 |
| 打包链 | `pyinstaller --onedir --collect-all rapidocr --collect-all onnxruntime` | 已有现成命令（`npm run build-py`），无 spec 文件（被忽略） |
| 基准工具 | `tests/perf/`（档位×分辨率、行数梯度、CPU 采样） | 改动可**当天验证**，不用重新发明测法 |
| 精度工具 | `python/bench_images` 48 张（模糊/JPEG/降采样/深色/低对比/11px）+ `bench_ocr.py`（CER/EM） | 有现成的精度门禁，量化掉点风险可控 |
| 源码调试入口 | `OcrBridge` 支持 `SCREEN_OCR_PYTHON` / `SCREEN_OCR_SCRIPT` 覆盖（0.2.2 为测试加的） | **改 Python 逻辑可先在源码模式验证，不必每次重打 395 MB sidecar** |

一句话：**这台机器具备把 A/B/C 三条都闭环验证的条件**，唯一缺的是一次性 Python 环境（约 5–10 分钟）。

## 2. 候选方案可行性判定

判定维度：要不要重打 sidecar、要不要新增依赖、本地能否闭环验证、对安装包体积的影响。

| 方向 | 需重打 exe | 新增依赖 | 本地可闭环验证 | 体积影响 | 判定 |
|---|---|---|---|---|---|
| **A1 线程自适应** | ✅ 需要（改的是 exe 里的代码） | 无 | ✅ 源码模式 + 重打后复测 | 0 | **可做** |
| **B1 det small + rec medium** | ✅ 需要（`build_params` 在 exe 内） | 无（模型已在包内） | ✅ | **−50 MB**（det medium 60M 不再需要） | **可做** |
| **C1 rec INT8 量化** | ❌ **不需要**（换 onnx + 改 yaml 里的 SHA256） | 仅构建期 `onnx`（运行期无） | ✅ `tests/perf` 直接测 | **−30~50 MB**（74M → ~20M） | **可做，且最划算** |
| D1 rec 宽度分桶 | ✅（改 rec 调用） | 无 | ✅ | 0 | 可做，排 P1 |
| D3 去抖/缓存 | ❌（主进程/渲染层即可） | 无 | ✅ | 0 | 可做，半天 |
| D4 预热推理 | ✅ | 无 | ✅ | 0 | 顺手做 |
| E1 两段式渐进 | ❌（主进程 + 渲染层 + 协议） | 无 | ✅ 但回归面大 | 0 | 0.3.0 再做 |
| F1 OpenVINO | ✅ 且需重新收集 DLL | **openvino（~300 MB）** | 可以，但打包易碎 | **+250~350 MB** | 本轮不做 |
| F2 DirectML | ✅ 且要换 ORT 发行版 | `onnxruntime-directml` | 能测，但机型差异大 | +50 MB | 本轮不做 |
| G1 蒸馏小模型 | ❌（只换模型） | 需要 GPU 训练管线 | **不能**（无训练条件） | 0 | 本轮不做 |
| G2 字段纠错 | ❌ | 无 | ✅（需样本） | 0 | 可做，收益窄 |
| A3 线程亲和 | ✅ | `psutil` 级依赖 | 可以 | 0 | 收益不稳，暂缓 |

## 3. 一个关键发现：INT8 可以**不重打包**先验证

这是本次筛选里最重要的一条可行性结论。

工程上本来以为「换模型 = 重打 395 MB sidecar」，但读了 rapidocr 的模型加载逻辑后可以绕开：

1. 模型解析走 `ch_ppocr_rec/main.py:35` 的 `DEFAULT_MODEL_PATH = rapidocr/models`，
   即 `python/ocr_pkg/ocr_server/_internal/rapidocr/models/`；
2. `inference_engine/onnxruntime/main.py` 在 `model_path` 为空时，用 `DownloadFile` 校验 **SHA256**：
   - 本地文件存在且 SHA256 命中 `default_models.yaml` → 跳过下载，直接加载；
   - **SHA256 不命中 → 会重新下载原模型**（离线时抛异常 → 回退 balanced）。

所以只要：**把量化后的 `PP-OCRv6_rec_medium.onnx` 覆盖同名文件，并把 `default_models.yaml` 里
`multi_PP-OCRv6_rec_medium` 的 `SHA256`（当前 `eef44482…894b`）改成新文件的值**，就能原地生效。
这两个都是**数据文件，不是编译产物**，不需要 PyInstaller。

> 附带一个坑：如果只换文件、忘了改 SHA256，表现是「启动时把量化模型覆盖回 fp32」——
> 离线时更糟，会抛异常并**静默回退到 balanced**（`new_engine` 的 fallback 逻辑），
> 看起来像「量化没效果」。验证时必须看 `ready` 里回报的 `profile` 是否仍为 `accurate`，
> `tests/perf/bench.js` 已经打印这一行。

## 4. 推荐方向

### 4.1 结论

**推 荐：A1（线程）+ B1（det 降级）+ C1（rec INT8）合成 0.2.4，先拿 4–5 倍；E1（两段式）留给 0.3.0。**

预期：高精度档 16.7s → **3–4.5s**；均衡档 0.9s → **0.6–0.7s**；安装包 272 MB → **约 210–230 MB**。

### 4.2 为什么是这三条

| 理由 | 说明 |
|---|---|
| **不需要任何新运行时依赖** | 三条都只动「已有代码 + 已有模型 + 一次离线量化」，不引入 OpenVINO/DML 这类重型依赖，符合项目「零新增依赖」的硬约束。 |
| **本地就能闭环验证** | 有 `tests/perf` 的速度基准、有 `bench_images` 的 CER 基准、有 `SCREEN_OCR_PYTHON` 源码模式，改动当天就能出数。 |
| **失败可秒回滚** | A1 是环境变量（不设即旧逻辑）；B1 是配置项；C1 是「把 fp32 的 onnx 拷回去 + 改回 SHA256」。三条都不需要改数据结构或协议。 |
| **同时减小体积** | B1 省 50 MB、C1 省 30–50 MB。项目现在安装包 272 MB 已经偏大，这轮是「提速 + 瘦身」，不是纯加速。 |
| **收益互补，不重叠** | A1 提「算力利用」、B1 砍「固定开销（2.7s 检测）」、C1 砍「每行成本（822ms→300ms 级）」，三条打的是不同的 84%/16%。 |

### 4.3 为什么**不**选另外几条（尽管它们单看更亮）

| 未选 | 理由 |
|---|---|
| **E1 两段式渐进（感知 10–20×，最诱人）** | 收益最大，但要改 sidecar 协议（同一 seq 两次结果）、主进程取消逻辑、渲染层原地替换，还要处理「行数变化导致选中位置跳动」。回归面覆盖 overlay/result/settings 三个页面 + 全部 43 项 UI 断言。**不是不能做，是不该和底层性能改动混在一个版本里**——两件事同时出问题会很难定位。建议 0.3.0 单独做，并配单独的验收（首次可见文字时间 ≤1s、行结构变化 ≤1 次）。 |
| **F1 OpenVINO** | 收益 1.5–2.5× 与 C1 同属「算力层」，叠加边际收益低；代价是安装包 +300 MB（272 → 570 MB）、只对 Intel 有效、PyInstaller 收集 DLL 易碎。且本轮目标是「先让高精度可用」，不是「榨干最后 30%」。 |
| **F2 DirectML** | 当前打包内**没有** DML provider（已核实 `onnxruntime/capi` 无 DirectML.dll），要换 ORT 发行版；收益高度依赖机型，无法在单机上定论。 |
| **G1 蒸馏** | 需要训练管线与标注数据，本地无 GPU 训练条件，周期以周计。当前瓶颈还没压到「模型能力」这一层，过早做属于越级。 |
| **A3 线程亲和 / D2 det 限幅一刀切** | 收益不稳（5–15%）且容易在别的机型上变差；D2 一刀切会伤小字，要按选区动态取值，复杂度不划算。 |

## 5. 风险与缓解

| 风险 | 触发条件 | 影响 | 缓解 |
|---|---|---|---|
| 重打包后行为漂移 | 依赖版本没钉死（rapidocr/onnxruntime/numpy 任一升级） | 速度/精度不可比，回归全乱 | 建 venv 时 **钉死 3.10.0 / 1.20.1 / 2.5.4**；打包后对 `_internal/*.dist-info` 做版本核对 |
| PyInstaller 产物结构变化 | 本机没有旧的 spec，靠命令重建 | 体积/启动变化，可能缺 DLL | 重打后跑 `tests/perf/bench.js` + `test_ocr_bridge_resilience.js`；对比 `_internal` 顶层目录清单 |
| INT8 掉点超预期 | 中文形近字、小字号 | 高精度「名不副实」 | 门禁：48 张 bench_images 的 CER ≤ 基线 +0.7pp、EM 降 ≤3pp；不达标就保留 fp32 |
| 量化后**反而变慢** | CPU 无 VNNI / 模型含不适合量化的算子 | 收益为负 | 先在 `tests/perf` 上 A/B，不达标直接放弃 C1，保住 A1+B1 |
| 忘了同步 `default_models.yaml` 的 SHA256 | 手工替换模型 | 启动时被覆盖回 fp32；离线则静默回退 balanced | 写成一个脚本（替换 + 改 yaml + 打印两边 hash），并把「`ready.profile` 必须为 accurate」写进验收 |
| 线程过多抢 CPU | 32 核机器开到 32 线程 | UI/系统卡顿，侧车反被调度抖动 | 默认 `min(cpu-2, 24)`、下限 2；保留 `SCREEN_OCR_THREADS` 可覆盖 |
| 低核机器劣化 | 4–8 核笔记本 | 新逻辑比旧逻辑慢 | 门禁里加一条「4 核下不劣化」（可用 `start /affinity` 模拟） |
| det small 漏小字 | 11–13px、低对比度截图 | 少检 1–2 个框，用户看到「少了行」 | 按字号分层测漏检率；必要时 `text_score` 0.45 → 0.40 补偿 |
| 安装包体积变化影响自动更新 | 体积从 272 MB 降到 ~220 MB | 增量更新 blockmap 变化，首次更新需全量 | 发布前核对 `latest.yml` 的 size/sha512 与新包一致（已有流程） |

## 6. 推进计划

### 阶段 0：环境（0.5 天）

```bash
# uv 不在 PATH 里，用绝对路径（本机已装）
UV=C:/Users/Lenovo/.local/bin/uv.exe
# 用 3.12 建隔离 venv（不污染系统 python）
"$UV" venv .venv-perf --python 3.12
# 钉死包内现役版本
"$UV" pip install --python .venv-perf/Scripts/python.exe \
  rapidocr==3.10.0 onnxruntime==1.20.1 numpy==2.5.4 onnx pyinstaller
# 源码模式跑一次，确认能复现基线（bench.js 已支持 SCREEN_OCR_PYTHON）
SCREEN_OCR_PYTHON=.venv-perf/Scripts/python.exe node tests/perf/bench.js
```

> `tests/perf/bench.js` / `bench-lines.js` / `probe-cpu.js` 三个脚本都会读 `SCREEN_OCR_PYTHON`：
> 设了就跑 `python python/ocr_server.py`，不设就跑打包版 exe。这样改参数可以在源码上先验证，
> 不必每次重建 395 MB 的 sidecar。

**出口条件**：源码模式跑出的 `accurate / 17 行 / 1280 宽` 与打包版基线（16.7s）同量级（±20% 内）。

### 阶段 1：A1 线程（0.5 天）

- 改 `python/ocr_server.py:62`：`threads = max(2, min(int(env or cpu-2), 24))`
- A/B：`SCREEN_OCR_THREADS=8 / 16 / 24`，看 `elapse_ms` 与占用核数
- **出口条件**：16 线程的 P50 至少比 8 线程快 1.5×；CER 无变化；4 核模拟下不劣化

### 阶段 2：B1 det 降级（0.5 天）

- accurate 只改 `Det.model_type` → small（rec 保持 medium）
- **出口条件**：`bench_images` 48 张 CER 劣化 ≤0.2pp、框数差异 ≤2%；`elapse_ms` 至少 −10%

### 阶段 3：C1 量化（1 天，可与 1/2 并行）

- 写 `python/tools/quantize_rec.py`：读 fp32 → `quantize_dynamic` → 写入 `python/quantized/PP-OCRv6_rec_medium.int8.onnx`
- 拷贝脚本同时完成「覆盖文件 + 更新 `default_models.yaml` 的 SHA256」
- **出口条件**：速度 ≥1.8×；CER ≤ 基线 +0.7pp；`ready.profile` 仍为 `accurate`

### 阶段 4：打包与回归（0.5 天）

- `npm run build-py` → `npm run dist`
- 全量：`npm test`、`test_result_ui`(43)、`test_i18n_ui`、`test_settings`、`test_ocr_bridge_resilience`、`test_settings_profile`
- 体积核对：sidecar 395 MB → 预计 320–350 MB；安装包 272 MB → 预计 210–230 MB
- **出口条件**：全绿 + 体积符合预期 + `latest.yml` 与产物一致

### 阶段 5：观察（1 周）

- 收集 `startup.log` 里的真实「引擎耗时 / 档位」，确认线上与基准一致
- 再决定 0.3.0 做 E1（两段式）还是 D1（分桶）或 F1（OpenVINO）

### 需要你拍板的三件事

1. **高精度目标值**：8s（只做 A1+B1）／4s（再上 INT8）／2s（还要 OpenVINO）。目标决定要不要做阶段 3。
2. **是否接受重打 sidecar**：一次 `build-py` 约 3–8 分钟，产物 395 MB，需要重装一次。若完全不想重打，只能做 C1（不重打）——但拿不到 A1 的 1.7×。
3. **安装包变小是否可接受作为发布卖点**：272 → ~220 MB，对分发是好事，但会改 `blockmap`，首次更新等同全量下载。

## 8. 一句话总结

在「32 核机器只用了 8 核 + 84% 时间花在逐行识别 + 检测有 2.7s 固定开销」这三个实测事实下，
**最合适的不是追求最亮的方案（两段式 / OpenVINO），而是先把算力闸门打开、把固定开销砍掉、把每行成本压下来**：
A1 + B1 + C1，零新增依赖、当天可验证、失败可秒回滚，还顺手把安装包瘦了 40–60 MB。
两段式感知方案排 0.3.0 单独做——它是「体验层的大招」，不该和底层性能改动混在一个版本里。

### 9.1 落地了什么

| 计划项 | 状态 | 说明 |
|---|---|---|
| A1 线程自适应 | ✅ 已上线 | `_threads()`：留 2 核、上限 24，`SCREEN_OCR_THREADS` 可覆盖 |
| B1 det 换 small | ✅ 已上线 | accurate 档 det=small / rec=medium |
| D4 预热推理 | ✅ 已上线 | `ready` 前显式跑一次 det+rec（模型是懒加载，构造 `RapidOCR()` 不建 session） |
| C1 rec INT8 | ❌ **未采用** | 速度达标、精度不达标，详见 9.3 |

### 9.2 实测

分阶段（`tests/perf/bench.js`，空白图 = 只跑检测）：

| 项 | 0.2.3 | 0.2.4 | 变化 |
|---|---:|---:|---|
| accurate 检测（空白图） | 2988ms | **405ms** | **7.4×** |
| accurate 17 行总计 | 13346–15242ms | 7348–9247ms | 约 1.8× |

> （同一份 0.2.3 侧车在 20:35 是 16.7s，21:40 复测到 24.5s）。所以本轮所有结论都取**同一次会话内的 A/B 比值**，
> 不跨时间点比较绝对值。

### 9.3 C1（INT8）为什么放弃

| 方案 | 体积 | 速度（裸推理 batch=12） | CER（18 张退化样本） | EM |
|---|---:|---:|---:|---:|
| fp32 | 73.1 MB | 基准 | **0.72%** | 77.8% |
| 动态量化 QUInt8 | 18.6 MB | **4.2–5.0×** | **7.94%** | 27.8% |
| + per-channel | 18.7 MB | 4.0× | 7.36% | 27.8% |
| + 仅量化 Conv | 31.4 MB | 3.2× | 7.22% | 27.8% |
| QInt8 | — | 无法加载（缺少 `ConvInteger` 实现） | — | — |

错例很典型：「小计」→「小针」、「苹果」→「翠果」、「香蕉」→「雪蕉」、「数量」→「数星」。
错误集中在**形近字**上，正是「高精度」档要避免的。按既定门禁（CER ≤ +0.7pp）判定不通过，
因此**保留 fp32**，量化工具留在 `python/tools/quantize_rec.py`（默认不启用，`sync_models.py` 需显式 `--int8`）。

> 一个反直觉点：只量化 Conv 也没救回来，说明掉点来自卷积权重量化本身，
> 而不是注意力层——这类 rec 模型（SVTR 系）对权重精度比预期敏感。

### 9.4 剩余瓶颈与下一步

0.2.4 里 accurate 的 8.9s 中，**检测只剩 0.4s，8.5s 全在 rec**（约 490ms/行，24 线程）。
下一步最值得试的是**级联识别**（不在原计划内，作为 0.2.5 候选）：

1. 先用 rec small 全量识别（约 22ms/行，17 行 ≈ 0.4s）；
2. 只把置信度低于阈值（如 < 0.85）的行，再用 medium 重跑；
3. 典型截图低置信行通常 10–20%，预计总耗时 1.5–3s，精度接近纯 medium。

代价：要在一个引擎里挂两个 rec session（内存 +25MB），并加一层「按行回退」逻辑。
这是目前唯一同时满足「≤3s」和「精度不掉」的路线，建议 0.2.5 做，并用同一套 `bench_ocr.py --set hard` 验证。

### 9.5 过程中遇到的两个坑（已修，写下来避免重犯）

1. **onnxruntime 量化器不支持中文路径**：它会在源文件旁生成 `xxx-inferred.onnx` 再读回，
   路径含中文时静默 `FileNotFoundError`。`quantize_rec.py` 已改为在 `C:/tmp` 下的 ASCII 临时目录里做。
2. **PyInstaller 重建会被「批量删除保护」拦下**：`--noconfirm` 会 `Removing dir python/ocr_pkg/ocr_server`，
   一次删 565 个文件触发安全拦截，构建以 exit 1 结束但**旧目录还在**（看起来像构建失败但产物没坏）。
   处理：先把旧目录改名成 `python/ocr_pkg_prev_<ver>/`（顺便当 A/B 的旧版基线），再构建。
   `scripts/build-py.js` 里已把这个判断留给人工，未做自动删除。

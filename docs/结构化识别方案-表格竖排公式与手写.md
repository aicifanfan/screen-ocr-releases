# 结构化识别方案：表格 / 分栏 / 竖排 / 公式 / 手写 / 艺术字

> 现状：只输出「行级文本 + 坐标」。表格变散行、分栏按坐标硬排、竖排认不出、
> 公式变乱码、手写基本不可用。本文给出分阶段落地方案。

## 0. 结论与分期

| 阶段 | 能力 | 技术选型 | 包体增量 | 单次耗时增量 | 预估 |
|---|---|---|---:|---:|---:|
| **A** | 版面分析 + 表格 → HTML/Markdown + 阅读顺序 | RapidLayout（YOLOv8/PP-Layout）+ RapidTable（SLANet+） | ~40 MB | 0.2–0.5s | 5–8 天 |
| **B** | 竖排（含列序从右到左） | 行方向判定 + 旋转识别 + 列重排（无新模型，或可选 RapidOrientation） | 0–30 MB | ~0 | 3–4 天 |
| **C** | 公式 → LaTeX | RapidLaTeXOCR（image_resizer + encoder + decoder） | **~170 MB** | 0.3–1s/公式 | 3–4 天 |
| **D** | 手写 / 艺术字 | 换识别模型 + 微调（无现成好用的中文手写 ONNX 行识别模型） | 20–80 MB | 同现有 | 评估 2 天，落地 1–3 周 |

**原则**：不换主引擎。现有 RapidOCR 继续负责「检测 + 行识别」，新增能力以**独立模块插在它前后**，
都跑在同一个 Python 侧车、同一个 onnxruntime 里，打包链路不变。

---

## 1. 为什么现在做不到

| 需求 | 现状原因 |
|---|---|
| 表格 | 只有 DB 检测的「行框」，没有单元格/行列关系；输出按 y 坐标排序 → 一行表格拆成 N 行文本 |
| 分栏 | 没有版面块概念，两栏文献会被按 y 交错串成一行 |
| 阅读顺序 | 只有「从上到下、从左到右」的简单排序，不区分标题/正文/表格/图注 |
| 竖排 | `Global.use_cls` 只管 0°/180°，不含 90°；竖排行送进横排识别模型 → 乱码 |
| 公式 | 公式被当普通文本行识别，输出是错乱字符 |
| 手写 / 艺术字 | PP-OCRv6 是印刷体模型，手写错误率高；艺术字属字体泛化问题，通用模型上限低 |

## 2. 总体设计

```
截图
 └→ [新] 版面分析 RapidLayout
       ├ 文档块（标题/正文/图注/表格/公式）
       └ 阅读顺序（按块，而非按行）
      ↓ 逐块处理
   ├ 文本块 ─→ 现有 det+rec（可选：竖排分支）
   ├ 表格块 ─→ [新] RapidTable → HTML → 可选 Markdown / 复制为 Excel 表格
   ├ 公式块 ─→ [新] RapidLatexOCR → LaTeX（$...$）
   └ 图片块 ─→ 占位（不识别）
      ↓
   结构化结果：blocks[] + 每块文本/HTML/LaTeX + 阅读顺序
      ↓
   结果页按块渲染；复制按「纯文本 / Markdown / HTML」三种格式
```

**关键设计**：版面分析要「可关」。它会让「框一个词复制」的场景多花 0.3s，
所以做成 `structured` 模式（默认走现在的快路径），只在用户选择「文档/表格」时启用。

## 3. 表格与分栏（阶段 A）

### 3.1 选型

| 库 | 模型 | 大小 | CPU 耗时 | 说明 |
|---|---|---:|---:|---|
| `rapid-layout` | YOLOv8 / PP-DocLayout / DocLayout-YOLO | 20–60 MB | 0.1–0.3s | 中英文版面，输出块类别 + 顺序 |
| `rapid_table` | `slanet-plus.onnx` | 6.8 MB | 0.15s/表 | 无线/有线表格 → HTML，含合并单元格 |
| `rapid_table` | `ppstructure_zh`（备选） | 7.4 MB | 0.15s | SLANet 旧版，中文表格 |

两个库都是 ONNX + onnxruntime，`rapid_table` 要求 `rapidocr>=3.0`（我们是 3.10.0，兼容）。
模型默认从 ModelScope 下载并做 SHA256 校验 —— 和我们现有的 `sync_models.py` 机制一致，
**新增模型要一并纳入构建期同步**，否则打包后又变成运行时下载。

### 3.2 输出与复制

- 结果页：表格块渲染成真实 `<table>`（而不是一堆行）；
- 复制格式三选一（工具栏加一个下拉）：
  - **纯文本**：单元格用 `\t` 连接、行用 `\n` → 粘到 Excel 自动成表；
  - **Markdown**：`| a | b |` + 分隔行 → 粘到 Typora/语雀；
  - **HTML**：直接写 `CF_HTML` 到剪贴板 → 粘到 Excel/Word 保留合并单元格。
- 分栏：按 layout 的块顺序输出，不再按 y 交错 —— 这是「阅读顺序」最直接的收益。

### 3.3 风险

- 表格模型对**跨行合并、嵌套表**仍会错，接受「大体正确、可手改」；
- 我们的图多是**应用界面截图**，不是扫描文档：版面模型在 UI 上可能把侧边栏当正文块。
  → 需要用自己的截图做一小批样本验证，必要时只在「检测到表格线/大面积文本块」时才走结构化。

## 4. 竖排（阶段 B）

没有现成的「中文竖排行识别」模型，但可以纯工程解决：

1. **判定**：对每个检测框，`height / width > 1.6` 且框内字符密度符合竖排 → 判为竖排行；
2. **旋正**：把裁剪图旋转 90°（顺时针/逆时针各试一次，取置信度高者）；
3. **识别**：送现有 rec 模型（横排）；
4. **重排**：同一块内的竖排行按 x 从**大到小**（中文竖排从右往左）排序，行内字符顺序保持旋转后的结果。

可选增强：引入 `RapidOrientation`（文档方向 0/90/180/270 分类，约 10–30 MB），
用于整图方向判错（比如截图是横着的照片）。这块改动只碰 `parse_output` 与排序逻辑，风险低。

## 5. 公式（阶段 C）

`rapid_latex_ocr`（ONNX）三个模型合计 **约 170 MB**：

| 模型 | 大小 | 作用 |
|---|---:|---|
| `image_resizer.onnx` | 37 MB | 预测输入分辨率档位 |
| `encoder.onnx` | 85 MB | 公式图像编码（ViT） |
| `decoder.onnx` | 49 MB | 自回归解码出 LaTeX token |

- 耗时：CPU 约 0.3–1s/公式（按公式复杂度）；
- 输出 `\frac{x^{2}}{a^{2}}-...`，复制为 `$...$`（行内）或 `$$...$$`（块级）；
- **触发方式**：靠 layout 的 `formula` 块类别；没有 layout 时退化为「用户框住的区域整块当公式」，
  提供「当作公式识别」的右键/按钮入口，避免误判把正文送进公式模型。

**包体代价**：+170 MB，安装包从 240 MB → **约 420 MB**。建议做成**可选组件**
（安装时勾选「公式识别」，或首次使用时下载），否则纯取字用户白背 170 MB。

## 6. 手写与艺术字（阶段 D，最难）

先说结论：**这两项没有「装个包就解决」的方案**，必须换模型或微调，且效果有天花板。

| 方向 | 可行性 | 做法 | 风险 |
|---|---|---|---|
| 手写（中文行） | 中 | 用 PP-OCRv5 的手写增强模型（若 RapidOCR 支持该 lang/version），或拿手写数据集微调 rec 模型 → 转 ONNX 接入 | 无现成 ONNX 权重；微调需 GPU 与标注；不同人字迹差异大 |
| 艺术字/字体泛化 | 低 | 换更大模型（medium 已用）+ 数据增强（字体合成渲染）微调 | 视觉风格无边界，投入产出比低 |
| 通用兜底 | 高（但有代价） | 视觉大模型（如 Qwen-VL 类）识别手写/艺术字很强 | **必须联网**，几 GB 权重不适合本地包；与「数据不出本机」冲突 |

**建议的落地顺序**：
1. 先把「可插拔识别引擎」抽象出来（`engines/` 下按能力注册），让手写可以走**独立模型**而不动主流程；
2. 用手写样本测一下 PP-OCRv6 medium 的真实 CER —— 如果只是「个别字错」，优先级放到最后；
3. 真要上，走「本机默认 + 联网 VLM 可选（明确提示会把裁剪图上传）」的双轨，默认关闭。

## 7. 输出与交互改动

| 位置 | 改动 |
|---|---|
| 结果页 | 支持「块」渲染：段落 / 表格 / 公式 / 图注；表格复用现有选中-复制机制（需要 `.item` 覆盖 table 单元格） |
| 工具栏 | 新增「识别模式」：通用（现状）/ 文档（结构化）；复制格式：纯文本 / Markdown / HTML |
| 剪贴板 | 新增 `CF_HTML` 写入（表格粘到 Excel 保留结构）；现有 `copyText` 保持 |
| 设置页 | 新增「启用表格/公式识别」开关（对应可选组件是否安装） |
| i18n | 新增约 12 个键（中英） |

**兼容性红线**：`texts/boxes/scores` 这套行级协议**保持不变**，结构化结果放在新字段 `blocks[]`，
老路径（复制全文、跨行选字、1 行=1 识别框）完全不受影响。

## 8. 打包与性能

| 项 | 影响 |
|---|---|
| 新增依赖 | `rapid-layout`、`rapid_table`、`rapid_latex_ocr`（都是纯 Python + ONNX，无 torch） |
| 包体 | +40 MB（A+B）→ +210 MB（含 C）；安装包 240 → **280 / 420 MB** |
| 内存 | 版面 ~50 MB、表格 ~30 MB、公式 ~120 MB（常驻仅在用时加载） |
| 耗时 | 结构化模式整屏：+0.4–1.5s（版面 + 表格）；公式每个 +0.3–1s |
| 线程 | 新模型与主识别抢 CPU → 复用现有「按模块分线程」机制，结构化模式默认 det 8 / rec 8 |
| 队列 | 结构化一次可能十几秒 → 必须沿用精修那套「可抢占 + 分批推送」，否则又会出现排队超时 |

## 9. 评测与验收

现有 `python/bench_ocr.py` 只测行级 CER，需要补结构化指标：

| 能力 | 指标 | 样本 |
|---|---|---|
| 表格 | 单元格准确率 + TEDS（结构相似度） | 20 张：有线/无线/合并单元格/带表头 |
| 阅读顺序 | 块顺序正确率 | 15 张：双栏、图文混排、侧边栏 |
| 竖排 | 字符准确率 + 列序正确率 | 10 张：竖排中文（含标点） |
| 公式 | 完全匹配率（归一化后） | 20 个：分式/上下标/求和/矩阵 |
| 手写 | CER（分人/分字体） | 30 行：不同书写风格 |

门禁：新增能力**不得让现有行级 CER 退化**（当前 medium 0.72%），结构化指标单独看板。

## 11. 明确不做的事

- **不引入 PaddlePaddle runtime**：PP-StructureV3 功能最全，但需要 paddle（+500 MB、CPU 更慢、PyInstaller 难打），
  与我们「离线 + 小包 + 纯 ONNX」的定位冲突。
- **不把 VLM 设为默认**：几 GB 权重 + 联网，和「截图不出本机」直接矛盾；只能作为显式开启的兜底。
- **不追求「全自动完美表格」**：合并单元格、嵌套表、跨页表仍会错，目标是「粘到 Excel 只需微调」。

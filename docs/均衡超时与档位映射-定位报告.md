# 「均衡比高精度还慢 / 均衡超时」定位报告

> 结论先说：**不是档位映射错误**。三档参数与模型映射经逐段核对完全正确；
> 用户看到的「均衡超时、高精度 1–2 秒」是**队头阻塞 + 测试顺序**造成的假象——
> 上一条高精度结果的后台精修还在跑，下一条请求（不管什么档位）都排在它后面，直到撞上 90 秒超时。

## 1. 参数链路逐段核对（前端 → 主进程 → sidecar → 模型）

| 环节 | 位置 | 实际内容 | 结论 |
|---|---|---|---|
| 下拉框取值 | `src/renderer/settings.html` | `value="fast" / "balanced" / "accurate"` | ✅ |
| 提交 | `settings.js` | `ocrProfile: optOcrProfile.value`（原样提交，无换算） | ✅ |
| 配置默认/持久化 | `src/main/config.js` | 默认 `balanced`；`update()` 替换对象，不做值映射 | ✅ |
| 变更才下发 | `src/main/index.js` | 快照旧值 → 变了才 `ocr.setProfile()` | ✅ |
| 桥接 | `src/main/ocr-bridge.js` | 发 `{"type":"setProfile","profile":p}`，等 `profileChanged` 回包后才改本地档位 | ✅ |
| sidecar 校验 | `python/ocr_server.py` | `if p in PROFILES and p != profile` → 重建引擎 | ✅ |
| 参数生成 | `build_params()` | 见下表 | ✅ |
| 模型实际加载 | rapidocr 日志 `Using *.onnx` | 与参数一致（见 §2 实测） | ✅ |

`build_params()` 的真实映射：

| 档位 | det | rec（首段） | rec（精修） | 备注 |
|---|---|---|---|---|
| `fast` | tiny | tiny | — | `limit_side_len=736` |
| `balanced` | small（默认） | small（默认） | — | 一次算完，**与 accurate 的首段完全相同** |
| `accurate` | small | small | medium | 两段式：先 small 全量，再分批 medium 精修 |

注意最后一行：**`balanced` 和 `accurate` 的首段是同一套模型**，
所以「均衡比高精度慢」在正常排队情况下物理上不可能发生。

## 2. 三档同图实测（1707×1067 全屏，det 出 97–103 个框）

| 档位 | 引擎耗时 | 行数 | 说明 |
|---|---:|---:|---|
| fast | **1.0s** | 103 | tiny 模型，一次算完 |
| balanced | **3.2s** | 97 | small 模型，一次算完 |
| accurate | **3.0s**（首段）→ 89s（精修完毕） | 97 | 首段与 balanced 同级，精修在后台 |

三档排序完全符合预期：fast < balanced ≈ accurate 首段 ≪ accurate 终态。
**没有任何一档的参数被接错。**

## 3. 那「均衡超时」到底是怎么来的

### 3.1 根因：单线程 sidecar 的队头阻塞

sidecar 是「一行一条消息」的单线程循环，而 `recognize` 的处理里**包含整轮 medium 精修**。
所以精修期间，后面到达的 `setProfile` 和下一条 `recognize` 全部堵在 stdin 里。

复现（`tests/perf/queue.js`，精修进行中再发一次识别）：

```
[修复前] seq=1 首包 2272ms → 精修 100118ms
         profileChanged 等了 99585ms
         seq=2 结果返回：等了 102282ms   ← 超过主进程 90s 请求超时 → 「识别超时」
[修复后] seq=2 结果返回：2429ms
```

主进程 `REQUEST_TIMEOUT = 90000`，所以只要上一轮精修还剩 >90 秒，
下一条请求必然报「识别失败：识别超时」——**与档位无关**。

### 3.2 为什么看起来「高精度反而快」

用户的操作顺序是「高精度 → 均衡 → 快速」，而每次高精度都会留下一条几十秒的后台精修：

1. **高精度**：首段 1–3 秒就出字，用户看到「快」；随后开始 60–100 秒的精修；
2. **均衡**：这次截图排在上一轮精修后面 → 等 ~100 秒 → **超时**；
3. **快速**：此时上一轮精修已结束/被丢弃，队列空了 → 又变成 1–2 秒。

所以「慢」跟着的是**测试顺序**，不是档位。同理，「快速 ≈ 高精度」也是因为两者的
用户可见耗时都由「首段/一次算完」决定，量级本来就在 1–3 秒。

### 3.3 附带的一个隐患

`setProfile` 也会被精修堵住：桥接 90 秒等不到回包会判定失败（设置页提示切换失败），
但消息仍在队列里，sidecar 稍后照样切换 → **UI 认为没切、引擎其实切了**。

## 4. 修复

| 改动 | 位置 | 作用 |
|---|---|---|
| stdin 改由独立线程读入队列 | `python/ocr_server.py` | 主线程不必阻塞在 `for line in sys.stdin`，可以「看到还有活」 |
| 精修每批之间检查队列 | `emit_refine_stream(..., pending=...)` | 有新请求就**提前收尾**（补一条 `final`，UI 正常收起提示），让路给新请求 |
| 回归脚本 | `tests/perf/queue.js` | 复现「精修中再截图」，断言新请求 <20s 且旧精修被提前收尾 |

效果：新请求最长只等**一批精修**（默认 8 行，约 2–5 秒），不再等整轮。

## 5. 验证方式

```bash
# 1) 参数映射：三档同图，看引擎耗时与模型（fast 1.0s / balanced 3.2s / accurate 首段 3.0s）
node tests/perf/latency.js --profile fast     --image shot-2560 --runs 2
node tests/perf/latency.js --profile balanced --image shot-2560 --runs 2
node tests/perf/latency.js --profile accurate --image shot-2560 --runs 2

# 2) 队头阻塞：精修进行中再发一次识别，必须 <20s
node tests/perf/queue.js --image shot-2560
node tests/perf/queue.js --image shot-2560 --exe python/ocr_pkg_prev_033/ocr_server.exe   # 旧构建应 FAIL

# 3) 应用侧：日志里现在会看到
#    [INFO] OCR 完成: N 行 | 引擎耗时 xxx ms | 端到端 xxx ms | 档位 fast|balanced|accurate
#    精修被让路时：sidecar 打印 warn「有新的请求在等待，本轮精修提前收尾（已完成 x/y 行）」
```

## 6. 结论

- **没有接错、没有映射错误**：三档参数、下发链路、模型加载都与设计一致。
- 真正的问题是**调度**：长任务（精修）在单线程队列里把后续请求饿死，撞上 90 秒超时。
- 修复后：档位切换与下一次截图最多等一批精修（2–5 秒），不会再出现「均衡超时」。
- 顺带消除一个状态不一致隐患：切档位不再可能因为排队而「UI 说失败、引擎却切了」。

# 高精度识别速度分析：瓶颈定位与剩余优化空间

> 全部数字来自本机实测（Intel/AMD 32 逻辑核 Windows，1707×1067 真实屏幕截图与 1300×700 选区），
> 驱动的是打包后的 `ocr_server.exe` 与真实 JSON 协议。绝对耗时会随机器负载漂移，
> **结论看比值与同一次会话内的 A/B**。

## 0. 结论摘要

1. 高精度档慢的主因**不是界面**（A/B 实测结果页渲染只差 3ms），也不是"行数多"，
   而是 **`识别框数 × 每框识别成本`**：medium 模型每**框**约 630–650ms，一次全屏能检出 64 个框 → 40 秒量级。
2. 存在两处**与精度无关**的浪费，其中一处是 0.2.4 我自己引入的：
   **线程数被统一设成 24**，对 det 与 small 这类小张量推理是纯亏（small rec 慢 3 倍、det 慢 1.6 倍）。
   0.3.2 改为按模块分配线程后，**均衡档全屏 1.84–2.63s → 1.23–1.38s**，高精度档首字与精修也一并改善。
3. 剩余可优化空间**集中在"少算行数"与"换推理后端/模型"**，两者都有明确代价；
   在线程、批大小、并行度这些"调度层"上，已经压到该机器的实际上限。

## 1. 成本模型（实测分解）

一次识别的耗时 ≈ `解码 + 检测(det) + 识别(rec × 框数)`。

全屏 1707×1067、检出 64 条文本（同一张图，分别测 det 与 rec）：

| 阶段 | 24 线程（旧） | 16/12 线程（新） | 说明 |
|---|---:|---:|---|
| det（limit_side_len=960） | 936ms | **588ms** | 只决定"框在哪"，与行数无关 |
| rec small（每框） | 43ms | **12ms** | 均衡/首段用的模型 |
| rec medium（每框） | 679ms | **598ms** | 高精度档的最终结果 |

**关键：`框数` 不等于 `你看到的行数`。**
真实屏幕截图 det 会出 64–168 个候选框（图标、菜单、状态栏都会被检），
最终过滤后留下的才是显示的行。省钱的地方在"少送框"，不在"少显示行"。

## 2. 三个瓶颈（按影响排序）

### 2.1 线程数"一刀切"（已修复，0.3.2）

`python/ocr_server.py` 原来只有一个全局线程数：`min(cpu-2, 24)`。
但三个模型的张量大小差一个数量级，最优线程数完全不同（48 个真实框，单位 ms）：

| 模型 | 8 线程 | 12 线程 | 16 线程 | 24 线程 | 32 线程 |
|---|---:|---:|---:|---:|---:|
| det small | 781 | 725 | **588** | 936 | 1084 |
| rec small | 678 | **595** | 766 | 1782 | 3385 |
| rec medium | — | 740 | **598** | 679 | 732 |

小张量开满 24 线程时，**线程同步开销超过了并行收益**：small rec 慢 3 倍，det 慢 1.6 倍。
0.3.2 改为按模块设定（det 16 / small rec 12 / medium 16，均可用环境变量覆盖）：

```
SCREEN_OCR_THREADS_DET=16
SCREEN_OCR_THREADS_REC=12
SCREEN_OCR_THREADS_MEDIUM=16
```

实测收益（同机、同图、同会话交错对比）：

| 场景 | 0.3.1 | 0.3.2 |
|---|---:|---:|
| 均衡档 · 全屏 64 行 | 1843 / 2632ms | **1233 / 1382ms** |
| 均衡档 · 选区 14 行 | 716ms | **597ms** |
| 高精度档 · 首字（全屏） | 1928 / 3670ms | **1828 / 1879ms** |
| 高精度档 · 精修（选区 14 行） | 9.6s | **8.8–9.0s** |

### 2.2 medium rec 的固有成本：约 630ms/行

这是"高精度"这个名字的价格，且**不受调度手段影响**：

- 与输入图片分辨率无关（960 宽与 2560 宽只差 2.6%）——det 被 `limit_side_len=960` 封顶，
  rec 只吃「宽高比」（等比缩到高 48）。**所以"先缩小图片再识别"这条路是死的。**
- 与线程数只到 16 就饱和（16→598ms，24→679ms，32→732ms）。
- 与并行度无关：拆成多会话并行跑（下表），基本没有收益。

### 2.3 检测框数量

| `Det.box_thresh` | 检出框数 | 备注 |
|---|---:|---|
| 0.3（当前） | 168 | 淡字也能检到 |
| 0.45 | 157 | |
| 0.6 | 129 | 会漏淡色小字 |

只降 23% 的框，却要承担漏字风险 → 不划算，**不建议动**。

## 3. 已验证无效的手段（不要再试）

| 手段 | 实测 | 结论 |
|---|---|---|
| 加大批大小 | batch 12→31.7s、24→29.8s、48→33.5s（40 行） | 收益 <10%，48 反而更慢（padding 变多） |
| 按宽度排序分批 | 28.3s（-11%） | 收益小，还要求结果回序，不建议 |
| 多会话并行（2×8 / 4×4 线程） | 20.6 / 19.0 / 21.0s | **无收益**，medium 已饱和 |
| INT8 动态量化 | 速度 4–5×，CER 0.72%→7.9% | 精度不达标（形近字全错），不采用 |
| 级联（small 全量 + 低分重跑 medium） | CER 与纯 small 相同 | small 的错误是**高置信**的，score 不能当可信度 |
| 长行切两半 | 1.2× | 边界切掉字符，风险大 |
| 降采样输入 | 无变化 | det 封顶 + rec 只看宽高比，原理上无效 |

## 4. 仍存在、可落地的优化空间

### A. 按模块分配线程 ✅ 已落地（0.3.2）

- **精度影响**：无。只是调度参数，模型与输入完全不变。
- **适用条件**：任何 CPU 推理；低核机器上 `_clamp_threads` 会自动夹到 `cpu-2`。
- **预期收益**：均衡/快速档 1.4–2.0×；高精度档首字 10–20%、精修 5–10%。
- **风险**：无（可用环境变量回退）。

### B. 精修结果分块流式推送 ✅ 已落地（0.3.3）

原来是：medium 全部算完才一次性推 `refined`，用户等的是**整块**结果。
0.3.3 改为每算完一批（默认 8 行，第一批 4 行）就推一条 `refined`，
用户从"第 1 行准确"到"最后一行准确"是渐进的。

- **精度影响**：无（最终仍是全量 medium，最后一条 `final` 包内容与一次性推送完全一致）。
- **适用条件**：高精度档；`SCREEN_OCR_REFINE_CHUNK` 可调批大小。
- **实测收益**（1707×1067 全屏，100 个框）：

  | | 一次性推送 | 流式推送 |
  |---|---:|---:|
  | 首次出字（small） | 3.5s | 3.5s |
  | **第一段准确文本** | **105.5s** | **5.5s** |
  | 全部算完 | 105.5s | 基本持平 |

- **实现约束**：每批的 `texts` 必须是「当前累计的完整数组」，行数从头到尾不变，
  否则主进程按行替换会错位、渲染层选中位置会跳。
- **风险**：批次之间会重建 DOM（已保留滚动位置）；用户正在选字时推迟到选区收起再替换；
  精修中途异常也要补一条 `final`，否则 UI 停在「精修中」。

### C. 换推理后端（OpenVINO EP）

- **精度影响**：无（同一 fp32 模型，算子级等价）。
- **适用条件**：Intel CPU；需把 openvino runtime 打进 sidecar。
- **预期收益**：同类 SVTR 模型上通常 1.3–2×；未在本机实测。
- **代价/风险**：安装包 +250–300MB；PyInstaller 收 DLL 易碎；非 Intel 机器无收益。

### D. 蒸馏 / 量化感知训练

- **精度影响**：可控（需评测门禁 `bench_ocr.py --set hard`，CER ≤ 基线 +0.7pp）。
- **适用条件**：需要训练数据与训练管线（本机无 GPU，周期以周计）。
- **预期收益**：2–3×（把 medium 的能力压到更好推理的模型上）。
- **风险**：投入最大，见效最慢；短期不排。

### E. 只精修"可能出错的行"（上限 -63%，但当前不可行）

实测：small 与 medium 结果**不同的行只有 29/78（37%）**，削掉其余 63% 的精修时间就是理论上限。
问题是**选不中**——small 认错的行往往置信度很高（已用 0.90 阈值验证过，几乎不触发重跑），
这是当前技术限制，不是实现问题。

## 5. 技术限制（为什么到此为止）

1. **medium 每框 630ms 是纯算力成本**：与分辨率、批大小、并行度都解耦，只能换模型/换后端；
2. **精度与速度在这个模型族里是硬跷跷板**：small 快 50 倍但 CER 从 0.72% 涨到 4.6–4.8%，
   INT8 快 4–5 倍但 CER 涨到 7.9%，且错误都是形近字（"小计→小针"），正是高精度档要避免的；
3. **没有"中等"重量级模型**：包里只有 tiny / small / medium 三档，medium 之上没有更优选择，
   medium 之下没有"精度介于两者之间"的档位——这是 RapidOCR v6 的模型谱系限制；
4. **CPU 上已无余量**：32 核机器上 rec 已用到 16 线程并饱和，再开线程是负收益；
5. **单进程串行**：sidecar 是单线程循环，精修期间再截图要排队（不是卡死）。

## 6. 怎么验收（复现命令）

```bash
# 1) 各阶段成本（det / small / medium 分开计时）
#    见 tests/perf/ 下的脚本与本文档第 1、2 节数据

# 2) 两段式端到端（首字 / 终态）
node tests/perf/latency.js --profile accurate --image shot-2560 --runs 3

# 3) 线程配置 A/B（不需要重打包，环境变量覆盖）
SCREEN_OCR_THREADS_DET=16 SCREEN_OCR_THREADS_REC=12 SCREEN_OCR_THREADS_MEDIUM=16 \
  node tests/perf/latency.js --profile balanced --image shot-2560 --runs 3

# 4) 精度门禁（任何模型/量化改动都要过）
.venv-perf/Scripts/python.exe python/bench_ocr.py --config v6_medium --set hard
```

> 注意：本机同时跑着 IDE / 视频等负载时，绝对耗时能漂 2 倍。**只看同一次会话内的交错 A/B 比值。**

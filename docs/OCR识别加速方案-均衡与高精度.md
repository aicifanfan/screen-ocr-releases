# OCR 识别加速方案 —— 均衡模式与高精度模式

> 版本基线：0.2.3（Electron 31.7.7 / RapidOCR 3.10.0 / onnxruntime CPU）
> 数据来源：本文所有数字均为**打包版 `ocr_server.exe` 实测**（非估算），测法与原始数据见 §1。
> 标注「预测」的部分是按实测斜率外推，落地时必须按 §5 复测。

---

## 0. 结论先行

高精度模式慢，不是「模型选大了」这么简单，实测拆开后是三个可以被单独攻击的瓶颈：

| 瓶颈 | 实测占比 | 一句话 |
|---|---|---|
| **检测（det medium）** | 2.74s / 16.7s ≈ **16%** | 输入被 960 封顶，**与截图分辨率无关**，是固定开销 |
| **识别（rec medium）** | 13.98s / 16.7s ≈ **84%** | 每行约 **822ms**，是均衡模式的 **37 倍**，慢在这里 |
| **线程只用 8 / 32 核** | 上限被硬编码 | `min(8, cpu_count)`，并行效率 97%，**加线程几乎线性收益** |

按性价比排，四条最该做的：

1. **线程数自适应**（改 1 行）→ 预测 **1.6–1.9×**，精度零影响，风险最低；
2. **det 换 small、rec 留 medium**（改 3 行配置）→ **−13%**，精度几乎无损（检测只决定框）；
3. **medium rec INT8 动态量化** → 预测 **2–3×**，CER 预计 +0.3~1pp，需按 §5 验收；
4. **两段式渐进识别**（先 balanced 秒出、accurate 后台替换）→ **感知提速 10 倍以上**，最终精度不变。

四条叠加，高精度模式端到端从 **16.7s → 3–4s**，用户感知从 **16.7s → 0.3–0.9s**。

**不要做的伪优化**：降采样输入（实测 960→2560 只差 2.6%，无效）、单纯调大 `rec_batch_num`（已 12，宽度差异会造成 padding 浪费）、加多进程 worker（单图无收益，内存翻倍）。原因见 §6。

## 1. 现状实测

### 1.1 测法

- 用**打包版** `python/ocr_pkg/ocr_server/ocr_server.exe`，走真实 JSON 协议（`SCREEN_OCR_PROFILE` 切档）；
- 每张图先预热 1 次（排除 ORT 图优化/内存分配），再取 2 次中的较快值；
- 样本：Canvas 渲染的 17 行中英混排「订单详情」截图（2560×1600 基准，按比例缩到 1600/1280/960）；
- 行数梯度：同一版式 1/4/9/17 行，1280×800 固定画布，用于求**每行边际成本**；
- CPU 采样：`TotalProcessorTime` 差值 ÷ 墙钟时间 = 平均占用核数。

### 1.2 分辨率扫描（同一内容，17 行）

| 档位 | 2560 宽 | 1600 | 1280 | 960 | 纯空白（只跑 det） |
|---|---:|---:|---:|---:|---:|
| fast | 271ms | 277ms | 256ms | 222ms | 105ms |
| balanced | 895ms | 738ms | 770ms | 721ms | 341ms |
| **accurate** | **13660ms** | 14472ms | 15242ms | 13346ms | **2988ms** |

### 1.3 行数梯度（1280×800）

| 档位 | 0 行 | 1 行 | 4 行 | 9 行 | 17 行 | det 固定成本 | rec 每行边际 |
|---|---:|---:|---:|---:|---:|---:|---:|
| fast | 64 | 81 | 99 | 134 | 195 | 64ms | **7.7ms** |
| balanced | 525 | 499 | 564 | 749 | 906 | 525ms | **22.4ms** |
| **accurate** | **2744** | 4249 | 5540 | 10654 | 16723 | **2744ms** | **822ms** |

> 边际成本 = (17 行 − 0 行) ÷ 17。0 行图只有检测、没有识别，因此差值就是纯识别成本。

### 1.4 算力利用（32 逻辑核）

```
fast      engine=  224ms  cpu=  2.03s  avg_cores= 8.99 / 32
balanced  engine= 1122ms  cpu=  8.98s  avg_cores= 7.98 / 32
accurate  engine=18016ms  cpu=139.91s  avg_cores= 7.76 / 32   ← 只用 1/4 的核
```

`python/ocr_server.py:62`：`threads = max(2, min(8, os.cpu_count() or 4))`。
8 线程跑出 7.76 核占用 = **并行效率 97%**，说明这不是「线程开多了在空转」，而是**被闸门卡住**：
放开到 16/24 线程，理论上能拿到接近线性的收益，直到内存带宽饱和。

### 1.5 三个反直觉结论

**① 对 accurate 档，降采样输入完全无效。**
960 宽 13.3s vs 2560 宽 13.7s，只差 2.6%。原因：det 侧已被 `limit_side_len=960` 封顶（检测成本恒定），
rec 侧的成本由**行数与宽高比**决定 —— `resize_norm_img` 把每行等比缩到高 48，
所以 crop 的绝对像素多少不影响推理，只有「宽/高」比值影响 padding 宽度。降采样不改宽高比，等于白做。
→ 任何「先缩图再识别」的方案对高精度无效（对 balanced 有 10–20%，因为小 det 对像素更敏感）。

**② 成本由「行数 × 宽高比」决定，不是「像素总量」。**
17 行长文本 = 14s 识别；同样画布 1 行 = 1.5s。所以「框少但框长」和「框多但框短」成本可能接近，
**减少送进 rec 的框数**（过滤噪声框、合并同行碎片）比压缩图片有效得多。

**③ det 是固定 2.7s 的「过路费」。**
只要选区大于 960，检测一律按 960 长边跑，2.7s 起步。小选区（如 400×200 取 2 行字）检测会快得多，
这也是「高精度只在小选区用」在成本上成立的原因。

## 2. 优化方向分项

字段说明：**场景**（什么时候适用）/ **收益**（相对 accurate 当前 16.7s）/ **精度**（影响）/ **开销**（CPU·内存·体积）/ **难度** / **风险** / **验证**。

### A. 执行器：线程与算子（投入产出最高）

#### A1. 线程数自适应（放开 8 核闸门）

| 项 | 内容 |
|---|---|
| 场景 | 所有档位；≥12 核机器收益最大（本机 32 核只用了 8） |
| 预期收益 | **1.6–1.9×**（16.7s → 9–10s）。依据：8 线程并行效率 97%，属计算密集型，线程数近似线性；32 核机器上 16 线程时内存带宽尚未饱和 |
| 精度影响 | **无**（同模型同输入，浮点结果可能有 1e-6 级差异） |
| 资源开销 | CPU 占用从 8 核升到 N 核；RSS 基本不变（ORT arena 已关） |
| 实施难度 | **极低**：`ocr_server.py:62` 改一行，并支持 `SCREEN_OCR_THREADS` 环境变量覆盖 |
| 风险 | 与用户其他程序抢 CPU（可留 2 核余量）；低核机器（4–8 核）收益归零；笔记本会更快掉电 |
| 验证 | 同图 A/B `SCREEN_OCR_THREADS=8/12/16/24`，记录 `elapse_ms` P50/P95 与平均占用核数；同时确认 CER 不变 |

建议实现：`threads = max(2, min(int(os.environ.get("SCREEN_OCR_THREADS") or 0) or (cpu - 2), 24))`，
即「留 2 核给 UI 与系统，上限 24」。

#### A2. inter_op 与 arena 策略微调

| 项 | 内容 |
|---|---|
| 场景 | 单模型串行推理（本项目就是这样：det→rec 顺序执行） |
| 预期收益 | **0–5%**，主要是减少空闲线程唤醒与内存抖动 |
| 精度影响 | 无 |
| 资源开销 | `enable_cpu_mem_arena=false` 已关（利于小内存），可保持；`intra` 已开，`inter_op` 建议锁 1 |
| 实施难度 | 低（配置项） |
| 风险 | 配错（如 `execution_mode=PARALLEL`）反而变慢 |
| 验证 | `elapse_ms` 波动区间是否收窄（看 P95，不看均值） |

#### A3. 线程亲和 / 大小核调度

| 项 | 内容 |
|---|---|
| 场景 | Intel 12 代以后的大小核 CPU（P 核 + E 核） |
| 预期收益 | 5–15%（避免推理线程被调度到 E 核） |
| 精度影响 | 无 |
| 资源开销 | 无额外，需平台 API |
| 实施难度 | **高**：Python 侧无标准方案，需 `psutil` 绑核或进程启动参数 |
| 风险 | 绑错核反而变慢；跨机型行为不一致 |
| 验证 | 对比绑 P 核 / 不绑的 P50；确认不同机型不劣化 |

### B. 模型组合：把两个阶段拆开选型（改动最小、最确定）

关键事实：det 占 16%，rec 占 84%，**两个阶段可以独立选型**。当前 accurate 是「双 medium」，
但两者的性价比完全不同。

#### B1. det 换 small，rec 保持 medium

| 项 | 内容 |
|---|---|
| 场景 | 高精度档的默认配置（建议直接改） |
| 预期收益 | **−13%**（16.7s → 14.5s）。det 从 2.74s 降到 ~0.52s（small 实测 525ms） |
| 精度影响 | **几乎为零**：检测只决定「框在哪、有几行」，文字本身的识别仍由 medium rec 完成。极端小字/低对比度场景可能少检 1–2 个框，可用 `text_score` 0.45→0.40 补偿 |
| 资源开销 | 模型体积 60MB → 9.5MB（安装包可减 50MB） |
| 实施难度 | **极低**：`build_params` 里 accurate 只改 Rec 的 model_type |
| 风险 | 密集小字（表格、代码）漏检率上升 |
| 验证 | `python/bench_images` 48 张退化样本，比较**框数**与 CER；要求 CER 劣化 ≤0.2pp、框数差异 ≤2% |

#### B2. rec 降级 + 提高输入分辨率（「小模型 + 大输入」）

| 项 | 内容 |
|---|---|
| 场景 | 想保留 1–2s 级速度、又不想丢掉 medium 的细节优势 |
| 预期收益 | **5–8×**（16.7s → 2–3s）：rec small 每行 22ms，即使把 `rec_img_shape` 高度 48→64、宽上限 320→640，也远低于 medium |
| 精度影响 | **需要实测**：多数场景 small@64px 能逼近 medium@48px，但形近字（0/O、l/1）仍可能退化。基准数据里 balanced CER 2.16% vs accurate 0.72%，差距主要在退化样本（模糊/低分辨率） |
| 资源开销 | 21MB 模型、内存降低 |
| 实施难度 | 低（配置项，但需重新校准 `rec_img_shape`） |
| 风险 | 「高精度」名不副实 —— 必须用 CER 数据说话，达不到就不能替换 |
| 验证 | 48 张基准 + 真实截图 30 张人工校对，要求 CER ≤ 1.0%（介于 balanced 2.16% 与 accurate 0.72% 之间且接近后者） |

#### B3. 三档重新定义（fast / balanced / accurate → 四档）

| 项 | 内容 |
|---|---|
| 场景 | 用户其实分不清「均衡」和「高精度」差在哪，档位语义需要重排 |
| 预期收益 | 间接：让 90% 的请求落在 1s 内的档位 |
| 精度影响 | 中性 |
| 资源开销 | 多一套模型组合（体积 +10MB 级） |
| 实施难度 | 中：新增 `accurate-lite`（small det + medium rec + 量化 rec），设置页文案与 i18n 同步 |
| 风险 | 选项过多导致选择困难 |
| 验证 | 灰度：统计各档位使用占比与平均耗时 |

### C. 量化与图优化（高精度模式的主力加速手段）

#### C1. medium rec INT8 动态量化

| 项 | 内容 |
|---|---|
| 场景 | 高精度档，CPU 无 VNNI 也可用（动态量化不需要校准集） |
| 预期收益 | **2–3×**（rec 14s → 5–7s；整体 16.7s → 7–9s）。ONNX Runtime `quantize_dynamic` 对 conv/MatMul 密集的 rec 模型通常在 CPU 上有 2–4× |
| 精度影响 | 通常 CER +0.3~1.0pp。rec 输出的是分类 logits，INT8 权重量化对常见字符影响小，形近字略增 |
| 资源开销 | 模型 74MB → ~20MB；推理内存下降；**打包体积减小**；无需 GPU |
| 实施难度 | 中：需要 `onnxruntime-tools`/`onnx` 在构建期跑一次量化脚本，产物入库；不改推理代码 |
| 风险 | 量化后掉点集中在低置信度样本；不同 CPU（AVX2 vs AVX512-VNNI）收益差异大；量化模型必须与 ORT 版本匹配 |
| 验证 | ① 48 张基准 CER ≤ baseline +0.7pp；② 真实截图 30 张逐字比对；③ 保留原 fp32 模型作为 fallback，测到掉点超阈值就回滚 |

#### C2. medium det INT8 量化

| 项 | 内容 |
|---|---|
| 场景 | 保留 medium det（若 B1 因漏检被否）时的替代方案 |
| 预期收益 | **1.5–2× 的 det 部分**（2.74s → 1.4–1.8s，整体 −6~8%） |
| 精度影响 | 检测对量化更敏感（框边界抖动），可能多切/少切行 |
| 资源开销 | 模型 60MB → ~16MB |
| 实施难度 | 中（同 C1，多一份产物） |
| 风险 | 框抖动会连带影响 rec 的 crop 质量，CER 可能非线性变差 |
| 验证 | 比较**框数、框 IoU 分布**与 CER；IoU<0.9 的比例上升超过 3% 则放弃 |

#### C3. 图优化落盘 + 固定输入形状

| 项 | 内容 |
|---|---|
| 场景 | 每次冷启动后首帧偏慢（ORT 做图优化 + 内存规划） |
| 预期收益 | 首帧 **100–300ms**（本机 init_ms 只有 12–19ms，说明模型加载已很快；收益主要在首帧推理） |
| 精度影响 | 无 |
| 资源开销 | 磁盘多一份优化后模型（+几十 MB，可选） |
| 实施难度 | 中：`session_options.optimized_model_filepath`，或用 ORT 的 EP context 缓存 |
| 风险 | 优化后模型与 ORT 版本绑定，升级需重建；缓存文件损坏会导致启动失败 |
| 验证 | 冷启动首帧 vs 热态首帧的差值是缩小还是持平 |

### D. 输入与调度（低成本、收益中等）

#### D1. rec 宽度分桶（按宽高比分组，减少 padding 浪费）

| 项 | 内容 |
|---|---|
| 场景 | 一屏里长短行混杂（表单、聊天记录、代码）——本项目典型场景 |
| 预期收益 | **10–25%**（只在 rec 部分）：`ch_ppocr_rec/main.py` 已按宽度排序，但一个 batch 内仍会 padding 到最宽行，一条长行就拖慢整批 12 条 |
| 精度影响 | 无（只是分批策略） |
| 资源开销 | 无 |
| 实施难度 | 中：不改 rapidocr 源码的话，需要在调用前把 `img_list` 按 ratio 分桶再分别调用；或 patch 其 batch 循环 |
| 风险 | 分桶过细会退化成 batch=1，反而更慢；需要按 `batch_num` 做折中 |
| 验证 | 在「长短混排」样本上比较 `elapse_ms`；确认 batch 利用率（平均 batch 大小）× 平均 padding 率下降 |

#### D2. det 限幅下调（960 → 736/640）

| 项 | 内容 |
|---|---|
| 场景 | 选区本身不大（<1200px 长边），或文字高度 ≥14px |
| 预期收益 | det 部分 **−40%**（面积比 0.59），整体 −6%（若仍是 medium det） |
| 精度影响 | 小字检测下降；`limit_type=max` 下 640 会让 12px 以下文字漏检率上升 |
| 资源开销 | 无 |
| 实施难度 | 极低（配置项），但**必须按选区尺寸动态取值**，不能一刀切 |
| 风险 | 一刀切会伤小字场景 |
| 验证 | 按字号分层（11/13/15/20px）测漏检率，确定「多少像素长边以下才降限」 |

#### D3. 请求去抖 / 取消 / 结果缓存

| 项 | 内容 |
|---|---|
| 场景 | 连续截图、误触重复识别、同一张图二次打开 |
| 预期收益 | 重复请求 **100%** 省掉；队列堆积时感知延迟大幅下降（历史日志出现过 49–120s 的排队） |
| 精度影响 | 无 |
| 资源开销 | 缓存按 LRU 保留最近 3–5 次结果，几十 MB 上限 |
| 实施难度 | 低：主进程已有 `pending` 机制，加「同 hash 命中即复用」「新请求到来时取消旧请求」 |
| 风险 | 缓存命中错误（截图内容相同但用户期望重新识别）——加「强制重试」入口 |
| 验证 | 连续截 5 次同一区域，观察引擎调用次数与总耗时 |

#### D4. 模型常驻 + 预热（已具备，需补 warmup 推理）

| 项 | 内容 |
|---|---|
| 场景 | 首次识别偏慢 |
| 预期收益 | 首帧 **200–400ms**（当前只做 `RapidOCR()` 构造，没有跑一次空推理） |
| 精度影响 | 无 |
| 资源开销 | 启动多占 ~1 次推理的 CPU（可异步） |
| 实施难度 | 低：`ready` 前跑一张 320×48 的空白小图 |
| 风险 | 启动阶段 CPU 抖动（放后台线程做） |
| 验证 | 冷启动首次识别的耗时 vs 第二次的差值 |

### E. 流水线与交互（不改模型，收益最大的是这一条）

#### E1. 两段式渐进识别（先快后准）

| 项 | 内容 |
|---|---|
| 场景 | 高精度档的所有场景，尤其是「用户盯着等结果」 |
| 预期收益 | **感知 10–20×**：0.3–0.9s 先出 balanced 结果，accurate 在后台重算并原地替换（16.7s → 用户 0.7s 就看到可用文本） |
| 精度影响 | 最终结果 = accurate，无损；中间态可能短暂显示低精度文本 |
| 资源开销 | 一次请求跑两遍（balanced 的额外成本仅 0.9s / 约 5% CPU），可接受 |
| 实施难度 | 中：sidecar 支持「同一 seq 两次结果」（`provisional` / `final`），渲染层做替换；主进程要能取消旧请求 |
| 风险 | 文本在眼前变化会让人误以为「识别错了又改」——需要弱提示（如标题栏小转圈 + 说明「正在精修」）；两次结果行数不同会导致用户选中位置跳动 |
| 验证 | 端到端录像：首次可见文字时间、结果稳定时间、以及行结构变化次数（应 ≤1） |

#### E2. 高精度「按需触发」

| 项 | 内容 |
|---|---|
| 场景 | 小选区取 2–3 行字（会议号码、验证码、报错信息） |
| 预期收益 | 大：小选区 det 成本从 2.7s 降到几十毫秒，端到端进入 1s 内 |
| 精度影响 | 无（仍是 medium） |
| 资源开销 | 无 |
| 实施难度 | 低：按选区像素面积/行数自动决定是否走 accurate，或设置页给「仅小选区使用高精度」开关 |
| 风险 | 用户预期不一致（大选区却降级）——需明确文案 |
| 验证 | 按选区尺寸分桶统计 P50 耗时与用户切换档位的频率 |

#### E3. 进度反馈与可取消

| 项 | 内容 |
|---|---|
| 场景 | 所有 >1s 的识别 |
| 预期收益 | 感知收益（不减少计算，但把「以为卡死」变成「明确在跑」） |
| 精度影响 | 无 |
| 资源开销 | 无 |
| 实施难度 | 低：遮罩页已有「正在识别…」，补进度阶段（检测中/识别 3/17 行）与 Esc 取消 |
| 风险 | 进度回调本身带来 IPC 开销（需节流，>100ms 一次） |
| 验证 | 主观 + 取消后 CPU 是否立即回落 |

### F. 运行时与硬件（收益大但有依赖代价）

#### F1. OpenVINO EP（Intel CPU）

| 项 | 内容 |
|---|---|
| 场景 | Intel 10 代以后 CPU，允许安装包变大 |
| 预期收益 | **1.5–2.5×**（OpenVINO 对 PP-OCR 系列有成熟优化，含 INT8 自动量化路径） |
| 精度影响 | 取决于是否启用 INT8；FP32/FP16 路径基本无损 |
| 资源开销 | 安装包 **+250~350MB**（openvino runtime）；内存略增 |
| 实施难度 | **中高**：需在 Python 依赖里加 `openvino`，PyInstaller 收集 DLL（易漏），打包后要验证不白屏 |
| 风险 | 打包体积与复杂度上升；非 Intel 机器上 EP 不可用需回退；与 rapidocr 的 openvino 后端版本匹配 |
| 验证 | 同图 A/B：ORT-CPU vs OpenVINO；检查是否真的走了 GPU/NPU（日志打印 device）；回退路径可用 |

#### F2. DirectML（iGPU / NPU）

| 项 | 内容 |
|---|---|
| 场景 | 有独显或较强 iGPU 的机器 |
| 预期收益 | 不确定：**可能 0**（模型小、搬运开销占比高），也可能是 3–5× |
| 精度影响 | FP16 累积误差，通常可忽略 |
| 资源开销 | 需要换成 `onnxruntime-directml` 包（当前打包内**没有** DML provider，已核实） |
| 实施难度 | 高：换 ORT 发行版 + 设备枚举 + 失败回退 |
| 风险 | 不同 GPU 驱动差异大；首帧编译开销高；打包体积 + |
| 验证 | 在 2–3 台有代表性的机器（NVIDIA/AMD/Intel iGPU）上测 P50，并确认无 GPU 时自动回退 |

#### F3. 电源与进程优先级

| 项 | 内容 |
|---|---|
| 场景 | 笔记本、节能模式 |
| 预期收益 | 5–20%（Windows 电源计划从「节能」切到「高性能」可显著改变 CPU 频率） |
| 精度影响 | 无 |
| 资源开销 | 功耗上升 |
| 实施难度 | 低（sidecar 进程设 `HIGH_PRIORITY_CLASS`）；改系统电源计划不建议（侵入用户设置） |
| 风险 | 高优先级可能让 UI 卡顿；用户不接受后台抢资源 |
| 验证 | 记录推理期间 CPU 频率与 `elapse_ms` 的相关性 |

### G. 模型侧长期工程（一次性投入大，长期收益最高）

#### G1. 蒸馏 / 裁剪专用 rec

| 项 | 内容 |
|---|---|
| 场景 | 只识别截图文本（中文 + 数字 + 常见符号），语种与字体分布窄 |
| 预期收益 | **3–5×**（专门的小模型可做到 small 级别速度、接近 medium 精度） |
| 精度影响 | 取决于蒸馏质量，通常可控制在 CER +0.2pp 内 |
| 资源开销 | 训练需要 GPU 与数据；产物只有 10–20MB |
| 实施难度 | **很高**：需要标注数据、训练管线、评测集；项目当前无训练能力 |
| 风险 | 过拟合到合成数据；维护成本长期存在 |
| 验证 | 独立测试集（不参与训练）CER/EM，且必须在真实截图上验证 |

#### G2. 后处理纠错（替代一部分「高精度」需求）

| 项 | 内容 |
|---|---|
| 场景 | 数字、金额、编号类文本（本项目典型：订单号、金额） |
| 预期收益 | 允许把 rec 降级到 small（**5–8×**），用规则/词表把误差补回来 |
| 精度影响 | 对结构化字段可能**不降反升**；对自由文本无效 |
| 资源开销 | 词典几 MB，CPU 可忽略 |
| 实施难度 | 中：需要字段识别（正则/上下文）+ 词表；已有 `postprocess_text` 可扩展 |
| 风险 | 过度纠正（把正确的改成错的）；规则维护成本 |
| 验证 | 在「订单号/金额/电话」样本上比对字段级准确率，而不是整段 CER |

## 3. 组合方案与预期

以 17 行截图为基准（16.7s）：

| 方案 | 组合 | 预期耗时 | 相对当前 | 精度预期 |
|---|---|---:|---:|---|
| **L1 低风险** | A1 线程 16 + B1 det small + D1 分桶 | **6.5–8s** | **2.2–2.5×** | 无损（CER 变化 <0.1pp） |
| **L2 推荐** | L1 + C1 rec INT8 | **3–4.5s** | **4–5×** | CER +0.3~1pp |
| **L3 激进** | L2 + F1 OpenVINO | 1.5–2.5s | 7–10× | 同 L2 |
| **P 感知方案** | E1 两段式（balanced 先出） + L1 | 首屏 **0.3–0.9s**，终态 6–8s | 感知 20× | 终态与 L1 一致 |
| **P+L2** | E1 + L2 | 首屏 **0.3–0.9s**，终态 3–4.5s | 感知 20×、终态 4–5× | 同 L2 |

**均衡模式**也能吃到 A1 + D1 + D4：0.9s → **0.6–0.7s**（约 1.3–1.5×），风险为零。

## 4. 优先级建议（按投入产出比）

### P0 —— 建议本迭代就做（改动小、收益确定、可回滚）

| 顺序 | 项 | 收益 | 工作量 | 为什么排前面 |
|---|---|---|---:|---|
| 1 | **A1 线程自适应** | 1.6–1.9× | 1 行 + 1 个环境变量 | 纯配置，精度零影响，所有档位通吃 |
| 2 | **B1 det small + rec medium** | −13% | 3 行 | 同样零精度风险，还能减小安装包 50MB |
| 3 | **E1 两段式渐进** | 感知 10–20× | 1–2 天 | 不牺牲精度就能让「慢」这件事消失，用户价值最高 |
| 4 | **D4 预热推理 + D3 去抖/缓存** | 首帧 −0.2~0.4s；重复请求 −100% | 半天 | 低风险，直接改善「点下去没反应」 |

### P1 —— 需要一次基准验证后再上

| 顺序 | 项 | 收益 | 前提 |
|---|---|---|---|
| 5 | **C1 rec INT8** | 2–3× | 48 张基准 CER ≤ +0.7pp；保留 fp32 回滚开关 |
| 6 | **D1 rec 宽度分桶** | 10–25% | 长短混排样本上验证，别把 batch 打散 |
| 7 | **E2 高精度按需触发** | 小选区进 1s | 产品文案与预期管理 |
| 8 | **C1b det INT8**（若 B1 被否） | det −30% | 框 IoU 分布不劣化 |

### P2 —— 收益大但成本/风险高，单独排期

| 顺序 | 项 | 收益 | 代价 |
|---|---|---|---|
| 9 | **F1 OpenVINO** | 1.5–2.5× | 安装包 +300MB、打包链改造、仅 Intel |
| 10 | **G2 字段后处理纠错** | 允许 rec 降级（5–8×） | 规则维护，只对结构化字段有效 |
| 11 | **F2 DirectML** | 不确定 | 换 ORT 发行版，机型差异大 |
| 12 | **G1 蒸馏小模型** | 3–5× | 需训练管线与数据，长期项目 |
| 13 | **A3 线程亲和** | 5–15% | 平台相关，收益不稳定 |

**一句话建议**：先做 P0 的 1+2+4（半天到一天，高精度从 16.7s 降到 8–10s），
再用 E1 把感知时间压到 1s 内；量化（C1）在有基准数据兜底后跟进。

## 5. 验证方案（每项改动都要过这一关）

### 5.1 指标

| 指标 | 采集方式 | 门槛 |
|---|---|---|
| 引擎耗时 | sidecar 返回的 `elapse_ms`，取 P50 / P95 | 不劣于基线；目标见 §3 |
| 端到端 | 主进程从 `capture:region` 到结果渲染 | 同上 |
| **CER / EM** | `python/bench_images`（48 张，含模糊/JPEG/降采样/深色/低对比度/11px） | 相对基线 **≤ +0.7pp**；EM 下降 ≤3pp |
| 框数与框质量 | 与基线比框数差异、IoU 分布 | 框数差异 ≤2%；IoU<0.9 占比上升 ≤3% |
| CPU / 内存 | 采样 `TotalProcessorTime`、Private Bytes | 线程提升后确认无异常尖峰 |
| 感知 | 首次可见文字时间（E1 必测） | ≤1s |

### 5.2 建议的 A/B 开关（便于灰度与回滚）

在 `ocr_server.py` 里把这些做成环境变量，默认值保持现状，便于同机对比：

```
SCREEN_OCR_THREADS        # 不设 = 老逻辑；设 16 = 新逻辑
SCREEN_OCR_DET_TYPE       # small / medium / tiny
SCREEN_OCR_REC_TYPE
SCREEN_OCR_DET_LIMIT      # 960 / 736 / 640
SCREEN_OCR_QUANT          # 1 = 用 INT8 模型（若已构建）
```

主进程侧用一个隐藏配置透传，方便「出问题一键回退」，不必重新发版。

### 5.3 回归门禁

1. `npm test` + `tests/test_result_ui.js`（43 项）+ `tests/test_ocr_bridge_resilience.js` 全绿；
2. CER 不超阈值；
3. 关闭量化时的 fp32 路径可正常启动（回滚可用）；
4. 低核机器（4 核）上不劣化 —— 这是 A1 最容易踩的坑。

## 6. 不建议做 / 已证伪

| 方案 | 为什么不做 |
|---|---|
| **降采样输入再识别** | 实测 960 vs 2560 只差 2.6%（13.3s vs 13.7s）。det 被 960 封顶，rec 只看宽高比，降采样不改比例 → 纯浪费，还可能伤小字 |
| **单纯调大 `rec_batch_num`** | 已设 12；batch 内 padding 到最宽行，长行会拖慢整批。不加分桶地继续调大只会增加 padding 浪费 |
| **多进程 / 多 worker 池** | 一次只识别一张图，进程间不共享内存；内存翻倍、模型重复加载（medium 双模型 134MB × N），收益接近 0 |
| **默认开启 accurate** | 与「快」的产品目标冲突；应改为「小选区自动 accurate」+ 两段式 |
| **换成 GPU 推理作为主线** | 打包内没有 DML provider（已核实），且目标用户机器差异大。GPU 只作为可选增强 |
| **缓存模型到内存反复重建引擎** | 切档位已有一次性 init 成本（12–19ms），重建不是瓶颈；真正的开销在推理 |

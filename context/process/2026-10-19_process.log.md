## P-02 · 15:30 · 对照实验（真实鼠标事件）

**环境准备（踩了两个坑）**
1. shell 里 `ELECTRON_RUN_AS_NODE=1`，直接跑 `electron main.js` 会退化成 Node，`app` 为 undefined → 必须 `env -u ELECTRON_RUN_AS_NODE`。
2. 默认 GPU 进程崩溃（`exit_code=-1073741819`）→ `app.disableHardwareAcceleration()` + `--no-sandbox` 后正常。

**实验设计**
- A 组：3 个独立 `contentEditable` div（现状复刻）。
- B 组：1 个 `contentEditable` 根 + 3 个块级子 div（候选方案）。
- 两组字体、行高、内边距完全一致；同一套指针序列：`mouseDown` → 8 次 `mouseMove`（带 buttons:1）→ `mouseUp`。
- 读取 `getSelection()` 的文本、字数、起止节点所属编辑主机。

**原始输出**
```
RESULT_A={"text":"\"一行识别文字 ABC 123\"","chars":12,"crossHost":false,"startHost":"item","endHost":"item","collapsed":false}
RESULT_B={"text":"\"一行识别文字 ABC 123\n第二行识别文字 DEF 456\n第三行识别文字 GHI 789\"","chars":38,"crossHost":false,"startHost":"c","endHost":"c","collapsed":false}
```

**结论**
- H1 成立：A 组拖过 3 行只选中第 1 行（12 字），选区在第一个编辑主机边界被钳制。
- 反证成立：B 组用同一套事件选中 3 行（38 字，含 `\n`）→ 排除「合成事件不可信」。
- 副产品：块级子节点之间 `toString()` 自带 `\n`，复制选中反而更符合预期。

**影响判断**
这不是审美问题，是**核心功能缺陷**。任何配色/动效方案都必须排在结构修复之后，否则是在坏地基上刷漆。

## P-03 · 15:32–15:36 · GitHub 资源调研

**方法**
逐个调 GitHub API 取 `stargazers_count / license / pushed_at / archived`，不凭记忆报数字；再按「能否与 contentEditable 共存」做第一道筛选。

**淘汰逻辑（按原因分组）**
| 原因 | 项目 | 关键事实 |
|---|---|---|
| DOM 包裹会破坏编辑与选区映射 | mark.js、web-highlighter | web-highlighter README 明确「splits and replaces text nodes」 |
| 选元素而非选文本 | selecto、DragSelect | 矩形命中 `getBoundingClientRect`，与原生文本选区互斥 |
| 已停止维护 | tippy（archived）、mark.js（dist 停在 2018）、selecto（2024-06 后无提交） | 不能作为长期依赖 |
| 能力冗余 | rangy、OverlayScrollbars | Blink 单引擎不需要兼容层；现有 `::-webkit-scrollbar` 已够 |
| 与渲染方式冲突 | auto-animate | 当前是 `innerHTML` 全量重建，接入需改渲染，收益为负 |
| 代价大于收益 | mobile-text-selection | 自绘手柄要接管原生选区，丢复制/输入法/无障碍 |

**保留的三样东西（都不引包）**
1. Radix Colors 的 12 阶语义色板 → 借「每一阶用途固定」的方法，解决本项目 5 层蓝色互相抢戏。
2. Open Props 的 easing/阴影值 → 只抄数值。
3. floating-ui 的 flip/shift 算法 → 若做选区浮条，手写 40 行即可。

**一个容易误判的点**
CSS Custom Highlight API 已是 Baseline 2026-03（Firefox 149 补齐），Electron 126 完全支持；但它只允许 `color / background / text-decoration / text-shadow`，**做不了描边、圆角、外发光**，所以「识别框」这类盒模型效果用不上它。

## P-04 · 15:37 · 视觉体系推导

**推导起点**
用户要「选中 / 未选中 / 拖拽中」三层一致。先列现状实际有几层蓝色：
`::selection #c9dcfd`、`.item.active #eff6ff`、`.box 6% / hover 14% / active 16%`。五层都在浅蓝区间，彼此差 1.1~1.4 倍对比度，人眼分不出优先级。

**得出原则**
> 全界面只有「文本选区」可以使用实色底；其余状态用描边、色条或 ≤12% 淡底。

理由：选区是用户主动操作的结果，必须视觉最强；联动指向是被动反馈，抢戏会让用户误以为「已经选中了」。

**量化验证（WCAG 相对亮度实算，不估）**
| 配对 | 结果 | 判定 |
|---|---|---|
| `#0b2b52` on `#c9dcfd` | 10.22:1 | 保留，已达 AAA |
| `#1f2937` on `#fff` | 14.68:1 | 保留 |
| `#64748b` on `#f8fafc` | 4.55:1 | 保留 |
| `#94a3b8` on `#fff`（空状态） | **2.56:1** | 不合格，改 `#64748b`→4.76:1 |
| `#15803d` on `#ecfdf5`（软成功态） | 4.76:1 | 可用 |

**顺带定位的交互问题**
- 拖拽时 `.item:hover` 逐行跟随 → 高亮"追鼠标"。
- 复制反馈换文案导致按钮宽度跳变 → 工具栏横向抖动。
- 识别框默认 6% 填充压住原图 → 对照阅读时发灰。

## P-08 · 15:57:08 · 视觉美化落地（实时）

**本轮约束（用户明确）**
- 保持现有页面结构与功能逻辑不变，只做视觉层优化；
- 不破坏数据绑定与交互行为。
- 因此**没有执行 T1（单容器重构）**，跨行拖选缺陷仍在，属已知限制。

**改动范围**
| 文件 | 性质 | 内容 |
|---|---|---|
| `src/renderer/result.html` | CSS 为主 | 令牌阶梯、工具栏状态、字体层级、识别框、响应式断点、高对比度 |
| `src/renderer/result.js` | 两处增补 | ① ResizeObserver 重算图片缩放 ② 复制反馈锁按钮宽度 |

**验证过程中发现并修掉的 4 个问题**
1. **过渡导致状态样式"读不到"**：`.item` 上的 `background-color` 过渡让同步 `getComputedStyle` 停在起始值（透明）。回归测试因此在「联动高亮」两项失败。
   → 去掉 `.item` 的过渡。这同时是视觉正解：拖选时背景应即时跟随，不应"追鼠标"。
2. **整行 2px 焦点环**（原样式）：实测 Chromium 下鼠标点击 contentEditable 也命中 `:focus-visible`，每点一行就出现一个像输入框的蓝框，与选区抢视觉。
   → `.item:focus-visible { outline: none }`，焦点反馈交给插入符。
3. **窄屏工具栏孤行**：`#status { flex-basis:100% }` 把「设置」挤到下一行且靠左。
   → 改为 `flex-basis:auto`，并让 `#btn-settings` 吃掉剩余空间（换行时靠右）。
4. **窗口变窄后图片不重算**：图片保持宽屏时的尺寸，出现横向滚动、识别框错位（原有限制，无 resize 处理）。
   → `ResizeObserver` 监听 `.img-panel`，复用既有 `drawBoxes` 重算；`renderAll` 时 `disconnect` 防止旧面板堆积。

**验证结果**
- `test_result_ui.js` 22 项全 PASS（可见窗口运行）。
  - 注：原测试以 `show:false` 运行时有 3 项「选区计数」失败，原因是隐藏窗口下初始 rAF 未执行导致 `selRaf` 卡住；与 CSS 无关，可见窗口下全部通过。
- `test_i18n_ui.js` 全 PASS（语言切换重绘路径未受影响）。
- 宽度 1120 / 700 / 440 / 390 实测：`pageOverflow=false`、`panelOverflow=false`，图片宽度始终小于面板宽度。
- 复制反馈宽度：81.33px → 81px（亚像素舍入），工具栏不再横向抖动。

**未做 / 待办**
- T1 单容器重构（结构问题）——按要求暂缓。
- T4 补测试（编辑根数量、user-select、按钮宽度稳定性）。

## P-15 · 18:45–19:20 · 「美化后变慢」定位与优化（0.2.2）

**现象**：用户反馈 0.2.1 界面美化后识别明显变慢。要求保持界面效果、提升识别效率与响应速度，并加强健壮性。

### 一、取证（先量再改）

1. **真实运行日志**（`%APPDATA%/screen-ocr/startup.log`，0.2.1 打包版）
   - `OCR 完成: 2 行 | 引擎耗时 2927.9ms | 端到端 2933ms | 档位 accurate`

   - 历史日志里还有 `引擎耗时 21~38s / 端到端 49~120s`：连续截图时请求排队（sidecar 串行）。
2. **A/B 渲染对比**（同一份数据：2 屏 × 2560×1600 JPEG + 各 30 行；软件渲染，复现 `disableGpu: true`）
   ```
   OLD(e7527e8) load=564ms items=28ms img=3ms
   NEW(current) load=561ms items=31ms img=8ms
   ```
   → 美化对渲染的影响 **+3ms**，页面加载持平，**不是瓶颈**。
3. **微基准**
   - 画布编码 2560×1600：PNG 41ms / JPEG 54ms（不值得为编码换格式）

## P-17 · 19:32–19:45 · 「切均衡还是很慢」根因：档位切换从未生效（0.2.3）

**用户反馈**：切换到均衡后仍然很慢，怀疑美化引入了性能问题。

### 一、日志给出的矛盾点

`%APPDATA%/screen-ocr/startup.log`（11:28–11:30，v0.2.2，配置已在 11:29:37 保存为 balanced）：

```
11:29:49 OCR 完成:  6 行 | 引擎耗时 6259ms  | 档位 accurate   ← 保存 balanced 之后
11:30:12 OCR 完成: 34 行 | 引擎耗时 14782ms | 档位 accurate   ← 还是 accurate
```
全日志 `grep "档位切换"` = **0 条**：`setProfile` 的 `.then` 从没跑过，说明调用压根没发生。

### 二、根因（配置对象被就地改写）

`src/main/config.js`：
```js
function update(partial) {
  Object.assign(load(), partial)   // 就地改写缓存对象
  persist()
  return load()
}
```

`src/main/index.js` `settings:set`（0.2.0 起一直如此）：
```js
const old = getAll()                          // old 就是缓存对象本身
...
update(partial)                               // 就地改写 → old 跟着变
if (partial.ocrProfile !== old.ocrProfile) {  // 永远相等 → 永远不成立
  ocr.setProfile(partial.ocrProfile)          // 从未执行
}
```

最小复现（`electron .tmp-probe/repro-alias.js`）：
```
保存前 old.ocrProfile = accurate
保存后 old.ocrProfile = balanced      ← 旧对象被改写
handler 里的判断 (partial !== old)： false (期望 true)
```

**结论**：设置页保存「均衡」只写进了 JSON，引擎仍在跑 accurate（medium 模型）。
accurate 在 1200×700、14 行的裁剪上实测 **24.0s**，balanced 只要 **1.61s**（15× 差距），
这就是"改了设置还是慢"的全部原因。

### 三、与「美化」的关系

- 该 bug 在 `e7527e8`（美化之前的「性能优化」提交）里就已经存在，不是界面改造引入的。
- 美化本身对渲染的影响在 P-15 已 A/B 量过：items 28→31ms、load 564→561ms，可忽略。
- 用户感知到的「美化后变慢」真实链条是：0.1.1 没有档位概念（始终 baseline）→ 0.2.x 引入档位，
  配置里落在 accurate（medium 模型，慢 10–15×）→ 想切回均衡却因上面的 bug 不生效。

### 四、修复

| 文件 | 改动 |

| `src/main/config.js` | `update()` 改为**替换**缓存对象（`cache = {...cache, ...partial}`），不再就地改写 |

**目标**：给「均衡 / 高精度」两档出可执行的加速方案，重点解决 accurate 档 10–24s 的问题。

### 一、先量再写（全部用打包版 exe，真实 JSON 协议）

分辨率扫描（同一版式 17 行，单位 ms）：

```
fast         271      277      256      222         105
```

算力采样（32 逻辑核）：

```
accurate 18016ms cpu 139.91s 7.76 核   ← 8 线程并行效率 97%，其余 24 核空闲
```

**三个反直觉结论**
1. **accurate 与输入分辨率几乎无关**（960→2560 仅差 2.6%）：det 被 `limit_side_len=960` 封顶，

2. **成本 = 行数 × 宽高比**，不是像素总量。减少送进 rec 的框比压缩图片有效。
3. **线程被硬编码卡在 8 个**（`ocr_server.py:62` `min(8, cpu)`），机器有 32 核 → 加线程近似线性收益。

## P-23 · 22:45–23:20 · E1 落地：两段式渐进识别（0.3.0）

### 一、设计

accurate 档拆成两段：small 跑完整流程 → **立即返回临时结果**；medium 对全部行重算 → 推 `refined`。
精度不变（最终结果就是 medium 算的），感知时间从 ~9s 降到 ~1s。

协议扩展（向后兼容）：
```
{"type":"result","seq":N,"stage":"provisional", ...}   ← small 结果，先上屏
{"type":"refined","seq":N,"texts":[...],"refine_ms":...} ← medium 结果，异步替换
```

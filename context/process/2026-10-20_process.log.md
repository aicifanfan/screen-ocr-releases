## P-26 · 高精度档为何慢：线程数一刀切（已修，0.3.2）

**背景**：用户质疑「0.3.1 没变」。核查后发现两层：
1) E1 只改善「首次出字」，最终结果确实没变；
2) 用户配置是 balanced，而两段式只对 accurate 生效 → 均衡档 0.3.1 与 0.2.4 完全一致。

于是重新做端到端剖析，找到了与精度无关的第二层原因。

### 一、取证方法（这次换了更硬的量法）

用 desktopCapturer 抓真实屏幕（1707×1067，det 出 64–168 个框），
直接喂打包版 `ocr_server.exe`（真实 JSON 协议），并把 det / small rec / medium rec 拆开计时；
所有 A/B 都在同一会话内交错执行（本机后台负载会让绝对值漂 2 倍）。

### 二、真实成本分解（48 个真实框，单位 ms）

```
模型         8线程   12线程  16线程  24线程  32线程
det small     781     725     588     936    1084
rec small     678     595     766    1782    3385
rec medium     -      740     598     679     732
```

**结论：0.2.4 引入的 `min(cpu-2, 24)` 对 det 与 small rec 是负优化**——
小张量开 24 线程，线程同步开销超过并行收益：small rec 慢 3 倍、det 慢 1.6 倍。
而 0.2.4 之所以看起来"有效"，是因为它针对的是 medium（大张量确实需要更多线程）。

### 三、改动（0.3.2）

`python/ocr_server.py`：
- `_clamp_threads()`（至少 1、至多 cpu-2、上限 32）
- 全局默认 24 → 16
- `_apply_module_threads(engine, det_thr, rec_thr)`：在建会话之前改写
  `EngineConfig.onnxruntime.intra_op_num_threads`（rapidocr 的 engine_cfg 是共享 dict，
  而 session 只在懒加载时读一次 → 先建 det、再改值建 rec，互不影响），异常静默回退全局
- 默认 det=16 / small rec=12 / medium=16，均可用
  `SCREEN_OCR_THREADS_DET` / `_REC` / `_MEDIUM` 覆盖
- `ready` 增加 `threads_det` / `threads_rec`

### 四、实测（同机同图、交错 A/B）

```

均衡档 · 选区 14 行    0.3.1: 716ms            0.3.2: 597ms
高精度 · 首字（全屏）  0.3.1: 1928 / 3670ms    0.3.2: 1828 / 1879ms
高精度 · 精修（14 行） 0.3.1: 9.6s             0.3.2: 8.8–9.0s
```

```
宽度排序    24+排序 → 28.3s（-11%，需回序，收益不足）
```

## P-27 · 精修分批流式推送（0.3.3）

**动机**：0.3.2 已把「首字」压到 1–3 秒，但那一版是小模型结果；medium 算完之前整块不更新。
100 行的全屏要等 ~105 秒，用户全程看的是临时文本 —— 这才是高精度档体验差的真因。

### 一、协议（向后兼容）

```
{"type":"refined","seq":N,"texts":[...],"scores":[...],
 "done":12,"total":100,"final":false,"refine_ms":...,"elapse_ms":...}
```
- `texts` 是**当前累计的完整数组**，行数从头到尾不变（否则主进程按行替换会错位、选中位置会跳）。
- 每批默认 8 行；**第一批只算 4 行**（用户从上往下读，先让顶部变准）。
- `final=true` 表示精修结束，UI 据此收起提示；老 sidecar 没有 `final/total` → 视为一次推完。
- 批大小 `SCREEN_OCR_REFINE_CHUNK` 可覆盖；精修中途异常也补一条 final（否则 UI 卡在「精修中」）。

### 二、改动

| 文件 | 内容 |
|---|---|
| `python/ocr_server.py` | `emit_refine_stream()`：分批 recompute + 逐批 emit；空结果/异常都保证有 final |
| `src/main/refined.js`（新） | `applyRefined()` 抽成纯函数（原在 index.js 内），便于单测；写入 `refiningDone`/`refineProgress` |
| `src/main/index.js` | 改为 `require('./refined')`；日志只记最后一条（13 条会刷屏） |
| `src/renderer/result.js` | `refining = provisional \|\| refiningDone === false`；提示文本带进度「精修中 12/64」 |
| `src/shared/i18n.js` | 新增 `result.refiningProgress`（中英） |
| `tests/fixtures/fake-ocr-server.js` | progressive 模式改为「1 行 → 2 行」两批推送 |
| `tests/test_progressive.js` | 8 → **14 项**（分批、seq 一致、行数不变、done 单调、final 标记、中间批只换已完成行） |
| `tests/test_result_ui.js` | 49 → **52 项**（批次到达不收起提示、显示 1/2 进度、final 才收起） |
| `tests/test_refined_merge.js`（新） | **19 项**：合并契约（部分/最终/老协议/空结果/多屏不匹配/单屏兜底/行数变化/非法输入） |

### 三、实测（1707×1067 全屏，100 个框）

```
一次性推送：provisional 3.5s → refined 105.5s（一次到位）
流式推送：  provisional 3.1s → 6.8s(4/100) → 10.7s(12) → 15.5s(20) → … → 97.4s(100, final)
```
**第一段准确文本 105.5s → 6.8s**，全部算完基本持平（略快，属噪声范围）。

## P-28 · 「均衡超时、高精度反而快」定位（0.3.4）

### 一、用户报告
切到「均衡」后识别超时；「高精度」1–2 秒；「快速」与高精度相近。
怀疑前端档位与后端参数接错。

### 二、逐段核对映射（结论：没有接错）

```
settings.html <option value="fast|balanced|accurate">
  → settings.js ocrProfile: opt-ocr-profile.value（原样提交）
  → config.js 默认 balanced，不做值映射（update 用替换，不就地改写）
  → index.js 快照旧值、变了才 setProfile
  → ocr-bridge.setProfile 发 {"type":"setProfile"}，等 profileChanged 回包才改本地档位
  → ocr_server.py `if p in PROFILES and p != profile` → new_engine(p)
  → build_params: fast=det tiny+rec tiny(736)；balanced=默认 small+small；accurate=det small+rec small→medium
```
三档同图实测（1707×1067，97–103 框）：fast 1.0s / balanced 3.2s / accurate 首段 3.0s + 精修 89s。
**balanced 与 accurate 的首段本来就是同一套模型**，「均衡更慢」物理上不可能。

### 三、真正的根因：队头阻塞

sidecar 单线程，`recognize` 处理里包含整轮 medium 精修；精修期间的 setProfile / 下一次 recognize 全排队。
复现（tests/perf/queue.js，精修中 1s 后再发识别）：

```
修复前：seq=1 首包 2272ms → 精修 100118ms；profileChanged 等 99585ms；seq=2 返回 102282ms（>90s 超时）
修复后：seq=2 返回 2429ms（shot-2560）
```

用户按「高精度 → 均衡 → 快速」测试，超时正好落在均衡那一步 → 看起来像均衡最慢。
附带隐患：setProfile 被堵到 90s 超时 → 设置页提示切换失败，但消息仍在队列里，sidecar 稍后照样切 →
**UI 认为没切、引擎其实切了**。

### 四、修复

| 文件 | 改动 |
|---|---|
| `python/ocr_server.py` | stdin 改由 daemon 线程读入 `queue.Queue`，主线程 `iter(inbox.get, None)` 消费 |
| `python/ocr_server.py` | `emit_refine_stream(..., pending=)`：每批之间检查队列，有新请求则 warn + 发 final 提前收尾 |
| `tests/perf/queue.js`（新） | 复现脚本 + 断言（新请求 <20s、旧精修 done<total、首包正常） |

### 五、验证

```

tests/perf/queue.js（旧构建 prev_033）：28277ms，精修跑满 17/17  FAIL（证明检查有效）
```

## P-31 · 「均衡截屏后一直卡在精修」定位与修复（0.3.5）

### 一、日志先证伪「均衡在精修」

```
10:42:09 切换 -> balanced
10:42:14 OCR 16 行 688ms 档位 balanced    ← 无 refined
10:42:41 OCR 32 行 842ms 档位 balanced    ← 无 refined
10:43:09 OCR 38 行 1111ms 档位 accurate
10:43:48 精修完成 38 行 38737ms           ← 精修只属于高精度
```
均衡档走的是非渐进路径，sidecar 根本不会发 refined；提示只可能来自上一轮的遗留状态。

### 二、根因

`show:result` 对每次结果都设 `refined = !provisional`，均衡档因此变成 `refined = true`。
渲染层 `shouldDefer` 的判据是 `refining && payload.refined === true && hasLiveSelection()`，
于是**新一次截图被误判为「精修替换」**：窗口还停在上一轮精修状态 + 用户有选区 → 延后 20s，
且每来一次更新就重置计时 → 表现为「一直卡在精修」。

### 三、修复

| 文件 | 改动 |
|---|---|
| `src/main/index.js` | `show:result` 显式 `refiningDone = !provisional`、`refineProgress = null`、`newResult = true` |
| `src/renderer/result.js` | `shouldDefer` 遇 `newResult` 直接返回 false；`onUpdate` 收到新截图先丢弃 deferredPayload |
| `src/renderer/result.js` | 看门狗 `armRefiningWatchdog()`：30s 无更新自动收起（阈值可被 `window.__refiningWatchdogMs` 覆盖供测试） |
| `src/main/refined.js` | seq 不匹配且结果里带 seq 时返回 false（不再兜底到唯一一屏），防止旧精修覆盖新截图 |

### 四、验证

```
结果页 52 -> 57 项（新截图在「精修中 + 有选区」时立刻替换、不继承旧提示、看门狗收起且不影响文本）
精修合并 19 -> 22 项（单屏 seq 不匹配必须丢弃）
负向验证：去掉 newResult 判断后，两条新断言立即 FAIL（文本停在「高精度临时一」）→ 复现用户症状
全量回归：npm test / 桥接 / 渐进 / i18n UI / 设置页 / 复制 / 多屏  全 PASS
```
